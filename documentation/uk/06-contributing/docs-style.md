# Стиль документації — як писати сторінки

> 📖 **In English:** [documentation/en/06-contributing/docs-style.md](../../en/06-contributing/docs-style.md)

Це **стислий виклад**. Повні правила, які забезпечуються при перевірці,
живуть у верхньорівневому **[STYLE.md](../../STYLE.md)** — прочитайте
його перед тим, як писати свою першу сторінку.

## Що ми пишемо

Документація фреймворку націлена на чотири аудиторії, у порядку
пріоритету:

1. **Автори модулів** — інженери, що пишуть бізнес-модулі. Основна
   аудиторія.
2. **Контриб'ютори фреймворку** — інженери, що змінюють код фреймворку.
3. **Інтегратори апаратури** — підключають плати й прив'язки.
4. **Оператори** — користуються WebUI / MQTT, але коду не пишуть.

Кожна сторінка має очевидно адресуватись одній із них. Якщо ви не
можете сказати, якій саме, — сторінці бракує фокусу. Перепишіть її.

## Двомовна політика

Кожна сторінка документації існує у **двох мовах**:

```
documentation/en/<path>/<name>.md
documentation/uk/<path>/<name>.md
```

Коли додаєте або редагуєте сторінку, **оновлюйте обидві версії**. Вони
дзеркальні за структурою і змістом. Допустимі відмінності:

- Блоки коду залишаються англійською (імена змінних, функцій, рядки
  логів).
- Коментарі всередині блоків коду можна перекласти, якщо це повчально.
- Перехресно зв'яжіть пару банером згори:

```markdown
> 📖 **In English:** [path/to/en/twin.md](../en/path/to/twin.md)
```

Не змішуйте мови в одній сторінці — оберіть одну й тримайтесь її.
Фрагменти коду — єдиний виняток.

## Анатомія сторінки (структурна конвенція)

```markdown
# `<name>` — <one-line summary>

> 📖 **Українською:** [twin link]

<2-4 paragraph introduction explaining what this thing is, why it
exists, AND when а reader should care>

REQUIRES: <dependencies, if а technical doc>

## <Section 1: most important first>

...

## Common pitfalls

<bullet list of bugs/confusions readers will hit>

## Next steps

<3-5 link bullets that the reader of THIS page is likely to need next>

## Source

<links to the underlying files: code, manifests, test fixtures, ADRs>
```

**Вступний абзац** відповідає: «що це? чому існує? хто має це читати?»
Розділ **Source** наприкінці каже, де живе істина. Кожна сторінка має
обидва.

## Сигнали для аудиторії

Пристосовуйте тон до аудиторії:

- **Автори модулів** — практично, «ви пишете `X`, фреймворк робить
  `Y`». Багато прикладів. Мало внутрішніх деталей.
- **Контриб'ютори фреймворку** — внутрішня будова, обґрунтування
  дизайну, компроміси. Посилайтесь на архітектурні рішення.
- **Інтегратори апаратури** — конкретне підключення, призначення пінів,
  рівні напруги.
- **Оператори** — навігація в UI, що роблять кнопки, без C++.

## Маркери статусу

У таблицях README:

| Document | Status | Purpose |
|---|---|---|
| existing.md | ✅ | Done. |
| planned.md | ⏳ planned | Stub OR scheduled. |
| existing.md | 🚧 WIP | Active rewrite. |

Коли завершуєте сторінку, змініть ⏳ на ✅ і переконайтеся, що
посилання на неї підключене.

## Перехресні посилання

- Завжди лінкуйте ІНШІ доки відносними шляхами:
  `[02-module-author-guide/manifest.md](../02-module-author-guide/manifest.md)`.
- Завжди лінкуйте файли ВИХІДНОГО коду глибокими шляхами від кореня
  документації:
  `[components/modesp_core/](../../../../components/modesp_core/)`.
- Не лінкуйте з тексту на абсолютні URL, якщо це не зовнішні ресурси.
  Усередині репозиторію — лише відносні.

Якщо посилання ламається через перейменування, виправте КОЖНУ сторінку,
що на нього посилається. `grep -r 'old_name.md' documentation/` — ваш
друг.

## Форматування

- **Markdown** (CommonMark + GitHub-таблиці). Без HTML, без MDX, без
  кастомних діалектів.
- **Заголовки** починаються з `##` після H1-назви. Ієрархія:
  H1 → H2 → H3. Пропуск рівнів допустимий, якщо це покращує ясність.
- **Блоки коду** з мітками мови: `cpp`, `bash`, `json`, `python`,
  `cmake`. Звичайний ``` ` ``` — лише для дуже коротких інлайн-фрагментів.
- **Таблиці** — для структурованих порівнянь (3+ позиції з 2+
  атрибутами).
- **Списки** — для кроків АБО варіантів. Уникайте пунктів довших за
  2 рядки.
- **Жирний** — економно, для акценту, не для прикраси.

## Обсяг

- **Сторінки посібника для авторів модулів** — 200–500 рядків.
  Вичерпно, з орієнтацією на робочий процес.
- **Сторінки посилання на компоненти** — 200–400 рядків. API + дизайн.
- **Сторінки посилання на модулі / драйвери** — 100–250 рядків. Поля
  маніфесту, типові помилки, вказівник на джерело.
- **Сторінки інструментів** — 150–300 рядків. CLI + інтеграція +
  типові помилки.
- **Концептуальні сторінки** — 150–300 рядків. Ментальні моделі.

Якщо сторінка наближається до 700 рядків — розбийте її.

## Стандарт якості (правила STYLE.md)

З верхньорівневого стайлгайду:

1. **Кожна сторінка відповідає на конкретне питання читача** — це
   зафіксовано у вступі.
2. **Показуйте, а не описуйте** — приклади перемагають прозу. Реальний
   код, не псевдокод.
3. **Перехресно посилайтесь на все** — кожне поняття посилається на
   свою сторінку-посилання.
4. **Вказівники на джерело обов'язкові** — кожна сторінка закінчується
   розділом Source.
5. **Двомовний паритет** — EN- і UK-версії відстежуються разом.
6. **Без мертвих посилань** — биті перехресні посилання провалюють
   рев'ю PR.
7. **Без маркетингової прози** — описуйте, що це робить, а не
   наскільки воно революційне.
8. **Не ховайте суть** — вступний абзац каже, чим є ця річ і чому
   хтось читає сторінку.

## Типові помилки

**«Дозвольте пояснити, як це працює»:** описуйте поведінку, а не
подорож. «X робить Y коли Z» краще за «спершу ми ініціалізуємо, потім
конфігуруємо, потім...»

**Забута синхронізація EN/UK:** редагуєте EN, забуваєте UK. Рев'юер
ловить; PR розгортають. Завжди редагуйте обидві в одному PR.

**Застарілі перехресні посилання:** перейменували сторінку, лишили
5 інших, що посилаються на стару назву. Запустіть
`grep -r 'old_path.md' documentation/`, щоб знайти їх.

**Блоки коду без міток мови:** нечитабельні в рендерах. Завжди
позначайте.

**Розмиті «see also»-секції:** «див. документацію» — марно. Конкретні
посилання з реченням, яке пояснює навіщо.
