# `encoder` — інкрементальний поворотний енкодер

> 📖 **In English:** [documentation/en/03-framework-reference/drivers/encoder.md](../../../en/03-framework-reference/drivers/encoder.md)

Інкрементальний поворотний енкодер — квадратурний (двопіновий A/B)
сенсор, що повідомляє, наскільки й у який бік повернули ручку. Драйвер
декодує сигнал CLK/DT на кожному такті й публікує **знаковий лічильник
детентів** як float. Споживач читає лічильник і відстежує його різницю
між читаннями, щоб виявити обертання; лічильник не скидається, тож кроки
не губляться.

Драйвер реєструється як `sensor` із `hardware_type: encoder` і
`requires_address: false`. Один сенсор на кожен прив'язаний енкодер.

Кнопку, що є на більшості модулів-енкодерів (KY-040 і подібні), цей
драйвер **не** обробляє — це звичайний контакт. Прив'яжіть пін SW до
драйвера [`digital_input`](digital_input.md) як окрему роль. Так `encoder`
лишається односигнальним сенсором, як і всі інші драйвери.

REQUIRES: `modesp_hal`. Без зовнішніх залежностей.

## Ресурс плати

Квадратурному енкодеру потрібно **два** піни, тож він отримує власний тип
ресурсу в board.json (ресурси «один id — один пін» не описують
двопіновий пристрій):

```json
"encoders": [
  {"id": "enc_0", "clk": 25, "dt": 26, "pull": "up", "label": "Menu encoder"}
]
```

| Поле   | Значення |
|--------|----------|
| `id`   | Hardware id, на який посилається прив'язка. |
| `clk`  | GPIO каналу A. |
| `dt`   | GPIO каналу B. |
| `pull` | `"up"` (типово) або `"down"`. Більшість механічних енкодерів заведені на GND і потребують підтяжки вгору. |

HAL конфігурує обидва піни як входи; драйвер ніколи не торкається сирих
пінів. Див. [04-hardware/board-config.md](../../04-hardware/board-config.md).

## Прив'язки

«Енкодер з кнопкою» описується **двома** прив'язками — обертання
(`encoder`) і клац (`digital_input`):

```json
{
  "manifest_version": 1,
  "bindings": [
    {"hardware": "enc_0",  "driver": "encoder",       "role": "menu_nav",    "module": "equipment"},
    {"hardware": "enc_sw", "driver": "digital_input", "role": "menu_select", "module": "equipment"}
  ]
}
```

Отримані стан-ключі:

- `equipment.menu_nav` (float) — накопичений лічильник детентів, знаковий.
- `equipment.menu_select` (bool) — рівень кнопки.

Тут `enc_sw` — звичайний запис `gpio_inputs` у board.json.

## Налаштування

| Ключ | Тип | Типово | Примітки |
|---|---|---|---|
| `steps_per_detent` | int | 4 | Квадратурних переходів на один фізичний клац. Модулі типу KY-040 видають повний цикл (4) на детент; для точніших енкодерів задайте 1 або 2. Зберігається. |
| `invert` | bool | false | Поміняти напрямок обертання (CW ↔ CCW). Зберігається. |

## Provides

`{"type": "float"}` — поточний знаковий лічильник детентів, публікується
у `equipment.<role>`. Це **абсолютна** позиція, не покроковий приріст:
поверніть на один детент за годинниковою — лічильник перейде з `0` на `1`;
поверніть назад — повернеться до `0`.

## Шаблон: споживання бізнес-модулем

Споживач тримає останнє побачене значення й діє за різницею:

```cpp
// у вашому BaseModule::on_update:
float pos = state.get_or("equipment.menu_nav", 0.0f);
int32_t delta = (int32_t)pos - last_pos_;     // last_pos_ — поле класу
if (delta != 0) {
    last_pos_ = (int32_t)pos;
    // delta > 0 → за годинниковою, delta < 0 → проти годинникової
    menu_move(delta);
}
bool click;
if (state.get("equipment.menu_select", click) && click) {
    menu_select();
}
```

Виявлення фронту й прискорення лишаються у споживачі — драйвер публікує
**сиру позицію**.

## Як це працює

Декодер читає 2-бітний стан квадратури `(CLK << 1) | DT` на кожному такті
й шукає перехід у таблиці з 16 записів за індексом `(prev << 2) | curr`.
Кожен валідний перехід сірого коду — це ±1 чвертькрок; невалідні переходи
(брязкіт контактів, пропущений стан) дають 0 й ігноруються. Чвертькроки
накопичуються, доки не набереться повний `steps_per_detent`, тоді знаковий
лічильник змінюється на одиницю.

Опитування на такті ~100 Гц достатньо для ручки, яку крутять рукою. Для
енкодера, що крутиться машинно й аліасить на 100 Гц, напишіть варіант на
периферії PCNT.

## Виявлення

Немає. Прив'язки оголошуються вручну.

## Типові помилки

**Рахує подвійно або вдвічі повільніше:** `steps_per_detent` не збігається
з вашим енкодером. Якщо один клац рухає лічильник на 4 — задайте 4 (чи
скільки ваш енкодер видає на детент); якщо пропускає клаци — зменшіть.

**Зворотний напрямок:** піни CLK/DT переплутані, або просто потрібна інша
домовленість — задайте `invert: true` замість перепаювання.

**Плаваючі піни на старті:** без підтяжок декодер бачить шум. Задайте
`pull: "up"` у board.json (і перевірте, що на модулі є власні резистори,
якщо GPIO лише для входу — 34–39 на класичному ESP32).

**Швидке обертання пропускає кроки:** опитування на 100 Гц може аліасити
швидко прокручений енкодер. Прийнятно для ручок меню; не для
високочастотного зчитування валу.

## UI

Немає у поставленому маніфесті. Додайте блок cards у своєму форку, щоб
відкрити `<binding_id>.steps_per_detent` / `<binding_id>.invert`, якщо
операторам треба підлаштовувати їх у полі.

## Чому варто прочитати цей драйвер

- Показує, як **багатопіновий** пристрій отримує власний ресурс board.json
  і HAL-finder (`find_encoder`) — шаблон для будь-якого сенсора, що його не
  описати ресурсами «один id — один пін».
- Чистий односигнальний контракт `sensor`, попри декодування стану між
  тактами: уся машина станів живе в драйвері, споживач бачить один float.
