# ADR-0006: Без вбудованих ContinuousBehaviors у MVP

> 📖 **In English:** [documentation/en/03-framework-reference/scenario-engine/adr/0006-no-builtin-continuous-behaviors.md](../../../../en/03-framework-reference/scenario-engine/adr/0006-no-builtin-continuous-behaviors.md)

**Статус:** заглушка. Повністю буде написано на Кроці 6 (continuous_registry).

## Стислий виклад рішення

Рушій постачає абстрактний базовий клас `ContinuousBehavior` + `ContinuousRegistry` для розширення, але **0 вбудованих реалізацій** у Stage 1 MVP. Доменні модулі (multicooker, thermostat тощо) реєструють власні (PID, гістерезис, ramp, cron) під час виконання через `ContinuousRegistry::register_factory()`.

## Розглянуті альтернативи

- **Вбудувати PID:** відхилено — рушій є доменно-агностичним; PID не універсальний (деякі продукти використовують bang-bang, fuzzy-логіку, model-predictive). Користувач явно сказав «без PID».
- **Вбудувати cron-усередині-фази:** відхилено — підтримка wall-clock відкладена; таймера, відносного до фази, достатньо завдяки умові `time_elapsed_ms` + переходам.
- **Відкласти весь інтерфейс ContinuousBehavior до Stage 1.5:** відхилено — рішення щодо дизайну інтерфейсу впливає на бінарний формат (поле `cont_count`, `cont_mask` для кожної фази). Краще зафіксувати інтерфейс зараз, навіть без реалізацій.

## Наслідки

- Рушій справді доменно-агностичний (немає поставлених поведінок, що натякають на конкретний кейс).
- ContinuousRegistry тестується юніт-тестами з мок-реалізаціями.
- Перший реальний ContinuousBehavior прийде з доменного модуля після MVP — це скеровуватиме доопрацювання інтерфейсу.
- Еталонний тестовий рецепт не використовує безперервні поведінки (cont_count=0).

## Посилання

- Директива користувача: «не вірне сприйняття концепції» (про те, що PID нібито центральний)
- План Q5 для сигнатури інтерфейсу
