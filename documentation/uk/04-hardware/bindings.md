# bindings.json — підключення драйверів до ролей

> 📖 **In English:** [documentation/en/04-hardware/bindings.md](../../en/04-hardware/bindings.md)

`bindings.json` — це **підключення, специфічне для розгортання**: який
тип драйвера обслуговує який апаратний вивід і яку семантичну **роль**
(ім'я на кшталт `air_temp`, `actuator_1`) він надає решті системи.
Якщо `board.json` каже "у мене є ці GPIO-виходи", то `bindings.json`
каже "GPIO-реле 1 — це actuator_1, спілкуйтеся з ним через драйвер
`relay`".

> **Роль = здатність, ніколи не драйвер (R0.1).** Роль приймає своє
> залізо за **capability** (temperature / relay_out / …) і напрямом
> (in/out), а не за іменем драйвера (R3.1). `driver` у прив'язці лише
> каже, *чим саме* створити екземпляр для цього конкретного заліза;
> модуль-споживач ролі ніколи не знає драйвера. Один і той самий
> термостат бере «температуру» байдуже від `ds18b20`, `ntc` чи
> майбутнього BLE-каналу. `address` (де є) обирає **канал** усередині
> цього заліза (напр. ROM-адреса конкретного сенсора на шині) — не
> ідентичність пристрою.

Ця сторінка — довідник для написання прив'язок із реальними прикладами
з референсних плат dev і KC868-A6.

## Де bindings.json у конвеєрі

```
   board.json              bindings.json            модулі
   ─────────               ─────────────            ──────
   "GPIO 14 існує"   →    "GPIO 14 — actuator_1  →   read_bool("equipment.actuator_1")
                          під керуванням драйвера relay"
```

Три частини відокремлені:

1. **Можливості плати** залишаються незмінними для ревізії апаратури.
2. **Прив'язки** змінюються залежно від розгортання (холодильна камера,
   теплиця чи пивоварня можуть використовувати ту саму плату з різними
   призначеннями ролей).
3. **Модулі** дбають лише про імена ролей (`equipment.air_temp`,
   `equipment.req_actuator_1`) — вони не знають, який GPIO чи який
   драйвер постачає дані.

Ви змінюєте прив'язки без перебудови прошивки — закидаєте новий
`bindings.json` у LittleFS через OTA або через редактор прив'язок у
WebUI (планується), і відображення ролей оновлюється.

## Розташування файлу

```
boards/<board_name>/bindings.json
```

Обирається разом із `board.json` через Kconfig `CONFIG_MODESP_BOARD=...`.
Обидва файли копіюються до LittleFS під час складання. Шлях під час
виконання: `/data/bindings.json`.

## Структура верхнього рівня

```json
{
  "manifest_version": 1,
  "bindings": [
    // ... масив об'єктів прив'язки
  ]
}
```

І все. Один масив. Кожен об'єкт у масиві — це одна прив'язка: екземпляр
драйвера, прикріплений до одного апаратного виводу / каналу / адреси.

## Анатомія однієї прив'язки

```json
{
  "hardware": "ow_1",         // id з board.json (який вивід / шина / вивід розширювача)
  "driver": "ds18b20",        // тип драйвера для створення
  "role": "air_temp",         // логічне ім'я — з'являється як equipment.<role> у SharedState
  "module": "equipment",      // модуль, що споживає цю прив'язку (майже завжди "equipment")
  "address": "28:8C:5E:...",  // опціональна ROM / додаткова адресація
  "settings": {"offset": 0.5} // опціональні налаштування драйвера для цієї прив'язки (див. нижче)
}
```

| Поле | Тип | Обов'язкове | Примітки |
|---|---|---|---|
| `hardware` | string | так | Має відповідати `id`, оголошеному у `board.json` (будь-яка секція: `gpio_outputs`, `onewire_buses`, `expander_outputs` тощо). |
| `driver` | string | так | Має відповідати імені драйвера, оголошеному у `drivers/<name>/manifest.json`. |
| `role` | string | так | Семантичне ім'я. Роль приймає це залізо за **capability**, не за драйвером (R0.1/R3.1). Стає `equipment.<role>` (сенсори) або `equipment.req_<role>` (актуатори) у SharedState. |
| `module` | string | так | Модуль, що володіє прив'язкою і оголошує роль (сьогодні: майже завжди `"equipment"`; connect-драйвери на кшталт `display`/`player` оголошують роль у своєму модулі). |
| `address` | string | іноді | Обирає **канал** усередині заліза (ROM 1-Wire, додаткова адресація I²C) — не ідентичність пристрою. Обов'язкове, якщо маніфест драйвера декларує `"requires_address": true`. |
| `settings` | object | опціонально | Налаштування драйвера для цієї прив'язки — див. нижче. |

### Налаштування для конкретної прив'язки

Маніфест драйвера може декларувати масив `settings` (кожен запис: `key`, `type`,
`default`, `min`/`max`). Прив'язка може перевизначити будь-яке з них об'єктом
`settings`; **пропущені ключі беруть значення за замовчуванням драйвера**, тож
`settings` завжди опціональний. Значення числові (int або float).

```json
{"hardware": "adc_1", "driver": "ntc", "role": "air_temp", "module": "equipment",
 "settings": {"beta": 3435, "r_series": 10000, "r_nominal": 10000, "offset": -0.3}}
```

Фабрика драйвера читає їх через `binding.setting_or("key", default)` і застосовує
в `apply_settings()`. Сьогодні: `ntc` враховує
`beta` / `r_series` / `r_nominal` / `offset` / `read_interval_ms`; `ds18b20` —
`offset` / `read_interval_ms`. Це **для кожної прив'язки окремо** — два NTC-датчики
на одній платі можуть мати різне калібрування. (Це замінює старі глобальні ключі
стану `equipment.ntc_*` / `equipment.ds18b20_offset`, які застосовували одне
калібрування до всіх датчиків і насправді ніколи не були під'єднані.)

## Конкретні приклади

### Плата dev — мінімальний сенсор + реле

`boards/dev/bindings.json`:

```json
{
  "manifest_version": 1,
  "bindings": [
    {"hardware": "ow_1",    "driver": "ds18b20", "role": "air_temp",   "module": "equipment"},
    {"hardware": "relay_1", "driver": "relay",   "role": "actuator_1", "module": "equipment"}
  ]
}
```

Ця плата має одну шину OneWire і чотири GPIO-реле, оголошені у
`board.json`. Ми прив'язуємо:
- Першу шину OneWire до драйвера `ds18b20`, роль `air_temp` —
  температура з'являється у `equipment.air_temp`.
- Перше реле до загального драйвера `relay`, роль `actuator_1` —
  керується через `equipment.req_actuator_1` (записи від бізнес-модулів)
  і відображається у `equipment.actuator_1` (поточний стан).

Зверніть увагу: **немає `address`** у прив'язці OneWire — драйвер
автоматично знаходить єдиний сенсор на шині. Якби сенсорів було кілька,
кожен потребував би окремої прив'язки зі своєю ROM-адресою.

### KC868-A6 — повний набір реле та входів

`boards/kc868a6/bindings.json`:

```json
{
  "manifest_version": 1,
  "bindings": [
    {"hardware": "relay_1", "driver": "pcf8574_relay", "role": "actuator_1", "module": "equipment"},
    {"hardware": "relay_2", "driver": "pcf8574_relay", "role": "actuator_2", "module": "equipment"},
    {"hardware": "relay_3", "driver": "pcf8574_relay", "role": "actuator_3", "module": "equipment"},
    {"hardware": "relay_4", "driver": "pcf8574_relay", "role": "actuator_4", "module": "equipment"},
    {"hardware": "relay_5", "driver": "pcf8574_relay", "role": "actuator_5", "module": "equipment"},
    {"hardware": "relay_6", "driver": "pcf8574_relay", "role": "actuator_6", "module": "equipment"},
    {"hardware": "din_1",   "driver": "pcf8574_input", "role": "input_1",    "module": "equipment"},
    {"hardware": "din_2",   "driver": "pcf8574_input", "role": "input_2",    "module": "equipment"},
    {"hardware": "din_3",   "driver": "pcf8574_input", "role": "input_3",    "module": "equipment"},
    {"hardware": "din_4",   "driver": "pcf8574_input", "role": "input_4",    "module": "equipment"},
    {"hardware": "din_5",   "driver": "pcf8574_input", "role": "input_5",    "module": "equipment"},
    {"hardware": "din_6",   "driver": "pcf8574_input", "role": "input_6",    "module": "equipment"},
    {"hardware": "ow_1",    "driver": "ds18b20",       "role": "air_temp",   "module": "equipment"},
    {"hardware": "ow_2",    "driver": "ds18b20",       "role": "temp_2",     "module": "equipment"}
  ]
}
```

Референсна плата прив'язує всю периферію KC868-A6 у **загальних** ролях:
шість виходів розширювача PCF8574 `relay_1`..`relay_6` стають
`actuator_1`..`actuator_6`; шість опто-входів `din_1`..`din_6` стають
`input_1`..`input_6`; дві окремі шини OneWire (`ow_1`, `ow_2`) дають
`air_temp` і `temp_2`.

Зверніть увагу: **немає `address`** у прив'язках OneWire — кожен сенсор
сидить сам на власній шині (`ow_1`, `ow_2`) і визначається автоматично.
Кілька сенсорів на *одній* шині потребували б явних ROM-адрес — див.
розділ нижче.

> **Загальні vs. семантичні ролі.** Загальні імена (`actuator_1`,
> `input_3`) описують *апаратуру*. Будуючи конкретний продукт, ви даєте
> тим самим виводам семантичні ролі — для холодильної камери це могли б
> бути `compressor`, `evap_fan`, `cond_fan`, `defrost_relay` на реле і
> `door_contact` на вході, плюс `evap_temp` на другому сенсорі. Змінюється
> лише цей файл прив'язок; плата і модулі лишаються тими ж.

## Кілька сенсорів на одній шині

OneWire — найпоширеніший випадок із багатьма пристроями. Кожен сенсор
має 64-бітну ROM-адресу (надруковану на корпусі сенсора в деяких
виробників, але зазвичай знайдену програмно). Прив'язки посилаються на
`id` шини (з `board.json::onewire_buses`) і вказують `address` для
кожного сенсора:

```json
{"hardware": "ow_1", "driver": "ds18b20", "role": "air_temp", "module": "equipment", "address": "28:8C:5E:45:D4:08:44:09"},
{"hardware": "ow_1", "driver": "ds18b20", "role": "temp_2",   "module": "equipment", "address": "28:40:0A:45:D4:72:7E:F0"},
{"hardware": "ow_1", "driver": "ds18b20", "role": "temp_3",   "module": "equipment", "address": "28:55:1B:35:E1:90:6A:24"}
```

Прапор `multiple_per_bus: true` у маніфесті драйвера повідомляє
фреймворку, що кілька прив'язок можуть націлюватися на той самий ID
`hardware`.

### Канали і вибір каналу у WebUI

`address` обирає **канал** capability-здатності. Генератор виводить для
кожної ролі `role.channels_by_driver` — список каналів, згрупований за
**обраним** драйвером, а не за роль-агрегатом (R3.5). WebUI показує
селектор каналів **лише** коли обраний драйвер дає 2+ каналів однієї
здатності; якщо канал один — він прив'язується автоматично, без зайвого
кроку. Тому per-driver атрибути (`requires_address` / `channels` / `scan`)
ключаться на **BOUND** драйвер: дротова прив'язка ніколи не вимагатиме,
скажімо, BLE-адреси лише тому, що якийсь *інший* драйвер тієї ж
здатності її потребує.

## Сенсори vs. актуатори у SharedState

Після завантаження прив'язок Equipment Manager породжує екземпляри
драйверів і виставляє ключі стану:

| Шаблон прив'язки | Згенеровані ключі SharedState |
|---|---|
| Сенсор (`category: "sensor"`) | `equipment.<role>` (поточне значення, лише для читання) <br> `equipment.<role>_ok` (справність, bool) |
| Актуатор (`category: "actuator"`) | `equipment.<role>` (поточний фактичний стан, лише для читання) <br> `equipment.req_<role>` (запитаний стан, доступний для запису) |

Тож запис `equipment.req_actuator_1 = true` — це спосіб, яким
бізнес-модуль вмикає актуатор. Equipment Manager читає ключ запиту,
передає його прив'язаному драйверу-актуатору і відображає фактичний
результат назад у `equipment.actuator_1`.

## Виявлення адрес

Для драйверів із `discovery.supported: true` у маніфесті фреймворк
виставляє ендпойнт сканування:

```bash
# Приклад DS18B20
curl -u admin:modesp http://192.168.1.85/api/drivers/ds18b20/scan
```

Повертає масив виявлених пристроїв з їхніми адресами і поточним
зчитуванням (корисно, щоб ідентифікувати фізично, який сенсор куди йде:
нагрійте той, який ідентифікуєте, рукою і слідкуйте за зростанням
показника).

```json
[
  {"address": "28:8C:5E:45:D4:08:44:09", "temperature": 22.5, "parasitic": false},
  {"address": "28:40:0A:45:D4:72:7E:F0", "temperature": 22.6, "parasitic": false}
]
```

Скопіюйте адреси у ваш `bindings.json`, перезберіть, прошийте.

Панель виявлення у WebUI (планується, коли з'явиться редактор прив'язок)
робитиме це автоматично — сканування, ідентифікація, перетягування у
прив'язки, збереження.

## Опціональні / резервні прив'язки

Прив'язки можуть оголошувати себе опціональними через поле `optional` у
секції `requires` маніфесту драйвера. Equipment Manager мовчки пропускає
відсутні опціональні прив'язки. Обов'язкові прив'язки, які не вдалося
розв'язати, перериваюсь запуск із повідомленням у журналі — тож
виробничі розгортання не працюють із мовчки зламаним обладнанням.

## Ідентичність — на пристрої, ніколи на прив'язці

`bindings.json` описує лише **дротове** залізо. Ідентичність віддалених
пристроїв (BLE MAC, майбутні LoRa devaddr / MQTT topic) **ніколи** не
живе на прив'язці ролі (R0.3) — інакше роль прив'язалася б до транспорту.
Такі пристрої додаються у **runtime** (скан → підписка на сторінці
«Пристрої»), пишуться у `/data/devices.json`, і роль резолвиться до них
за capability так само, як до дротового каналу. `Binding` тримає лише
device `id`; резолв `id → identity/name` робить `find_remote_device(id)`.

Тому референсний `boards/stand_s3/bindings.json` містить **тільки**
дротові прив'язки (дисплей `disp_0`, аудіо `i2s_0`), а всі BLE-пристрої
(Xiaomi/nRF-обсервери, iPixel-панель) додаються у runtime і прив'язують
ролі `room_temp` / `orientation` / `panel` вже там.

## Валідація

`generate_ui.py` перехресно валідує bindings відносно `board.json` + маніфестів
драйверів на етапі збірки — неправильна прив'язка ламає білд, а не тихо
пропускається в рантаймі. Кожна перевірка — ERROR:

1. Кожен `hardware` розв'язується в `id` у board.json (і в плати немає
   дублікатів id).
2. Кожен `driver` розв'язується в `drivers/<name>/manifest.json`.
3. **`hardware_type` драйвера збігається з секцією board його `hardware`** —
   напр. `ds18b20` (onewire_bus), прив'язаний до `adc_channel`, відхиляється.
4. Драйвер із `requires_address: true` має непорожній `address`. (`ds18b20` —
   `requires_address: false`: одно-сенсорний SKIP_ROM без адреси валідний.)
5. `hardware` id повторюється лише якщо драйвер `multiple_per_bus: true`, і тоді
   кожна прив'язка має окрему непорожню `address`.
6. `role` унікальна в межах модуля.

Окремо, білд прошивки **падає**, якщо активна плата прив'язує драйвер,
**вимкнений у menuconfig** (`CONFIG_MODESP_DRIVER_<NAME>=n`) — перевірка в
`components/modesp_hal/CMakeLists.txt`. Узгодити:

```bash
python tools/drivers_sync.py --fix          # увімкнути bound-but-disabled драйвери
python tools/drivers_sync.py --prune        # також вимкнути невикористані (менший бінарник)
python tools/drivers_sync.py --dry-run      # показати різницю, нічого не міняти
```

Білд також друкує `INFO:` зі списком драйверів, увімкнених, але не використаних
активною платою (виключаючи discovery-драйвери як `ds18b20`).

## Типові помилки

**Неправильний ID апаратури:** друкарська помилка у полі `hardware` —
board.json має `relay_1`, але bindings каже `Relay_1`. Складання
завершується помилкою "hardware ID 'Relay_1' not declared у board.json".
Виправлення: точна копія з урахуванням регістру.

**Невідповідність драйвера і категорії апаратури:** прив'язка
GPIO-виходу до драйвера сенсора (`ds18b20` очікує шину OneWire). Або
виправте драйвер, або виправте ID апаратури.

**Відсутня адреса для шини з кількома пристроями:** OneWire з 2+
сенсорами, але прив'язки без поля `address` — зчитування драйвера
підхоплюють той, що відповідає першим (зазвичай пристрій з найменшою
ROM). Жах для відлагодження — показники змішуються між сенсорами.
Завжди вказуйте ROM-адреси для шин із кількома пристроями.

**Дубльована роль:** дві прив'язки з однаковою `role` — Equipment
Manager падає при ініціалізації. Кожна роль має бути унікальною в
межах модуля.

**Редагування прив'язок без OTA / перебудови:** файл живе в LittleFS.
Зміни на хості, які не доходять до flash-пам'яті пристрою, не
дадуть ефекту. Перепрошийте, або скористайтеся заміною файлу через
OTA, або редагуйте через редактор прив'язок у WebUI (планується).

## Робочий процес для нового розгортання

1. **Визначте ваші ролі** на основі рецепту / варіанту використання.
   Референсна плата постачається із загальними ролями (`actuator_1`,
   `input_1`, `air_temp`); для конкретного продукту ви обираєте семантичні
   імена — напр. для холодильної камери: `air_temp`, `evap_temp`,
   `compressor`, `evap_fan`, `defrost_relay`, `door_contact`.
2. **Зіставте з апаратурою плати.** Подивіться у `board.json`, щоб
   побачити, що доступно — реле, шини OneWire, GPIO-входи.
3. **Оберіть драйвери** для кожної апаратури: GPIO-реле → `relay`;
   реле PCF8574 → `pcf8574_relay`; сенсор DS18B20 → `ds18b20`; сенсор
   NTC → `ntc`.
4. **Напишіть `bindings.json`** з однією прив'язкою на роль.
5. **Запустіть виявлення адрес** для OneWire / шин із кількома
   пристроями; скопіюйте адреси у прив'язки.
6. **Зберіть, прошийте, моніторте.** Перевірте, що ключ
   `equipment.<role>` кожної ролі з'являється у `/api/state` з
   осмисленими значеннями.
7. **Ітеруйте**, якщо щось не так — неправильно ідентифікований сенсор,
   інвертована полярність реле тощо.
