# AMT630A — OSD-рушій, модель BGMAP та 5 вікон (дослідницький звіт)

> **Скоуп:** OSD-архітектура AMT630A для відображення повного навігаційного меню ModESP **одночасно** з накладними сповіщеннями (overlay).
> **Джерела:** `ENGELS.A22` (OEM-дизасемблер, найбагатший — абсолютні адреси + імена `IO_OSD_*` + коментарі Korth), `AMT630A.A22` (чиста прошивка з sysgui-процедурами), `AMT630A_user_spec.md` (канонічна спека користувача), Fizik `AMT630.h` (доведений робочий I²C-драйвер).
> **Керування:** Шлях A (I²C ззовні), банк OSD `FBxx` → I²C 7-біт **`0x5B`**.
> Дата: 2026-06-14.

---

## 0. Резюме найважливішого

1. **BGMAP = лінійний масив 200h (512) слів.** Кожне слово = 10-біт № символу + 7-біт атрибут. Прошивка чистить його циклом `addr 0000h…01FFh` (`osd_zerofill_vram_200h_words`, ENGELS `AE3D`), і init теж проходить `r1=0…1`, `r0=100h` = 2×256 = 512 (AMT630A `init_OSD_hardware` `3864`). Це підтверджує «200h записів».
2. **Мапінг BGMAP-адреса ↔ клітинка — НЕ апаратний, а програмний:** `bgmap_addr = yloc*stride + xloc`, де `stride` визначає САМ драйвер (для 8px-шрифту прошивка бере stride=20). Апаратура лише авто-інкрементує `addr_lsb` при кожному записі `data_lsb`. Тобто розкладку клітинок задаєш ти.
3. **Кожне з 5 вікон — самостійний «спрайт»** з власними size/xy-loc/scale; вікно 0 особливе: BGMAP-адреса фіксована = 000h. Вікна 1-4 мають додатковий регістр `vramaddr_lsb` → довільне вікно у BGMAP. **Це і є механізм overlay.**
4. **Пріоритет = номер вікна:** вікно 0 — найвищий (поверх), 4 — найнижчий. (спека; узгоджується з тим, що вікно 0 фіксоване й використовується прошивкою для головного меню).
5. **Enable — один регістр FB05h** (bit0-4 = вікна 0-4, bit6 = TEXT on/off глобально, bit7 = BITMAP/4bpp).

## 1. Три області пам'яті OSD (ENGELS, спека)

| Область | Розмір | Призначення |
|---------|--------|-------------|
| **BGMAP RAM** | **200h слів (512)** | «екран»: слово = 10-біт № символу + 7-біт атрибут |
| **FONT RAM** | 1000h слів (~8 КБ) | завантажуваний шрифт (кирилиця/4bpp-графіка), № `1C0h+` |
| **FONT ROM** | 418 симв. 16×22 1bpp | вбудований: пробіл/цифри/лат./трохи кирилиці/бари |

**Формат слова BGMAP** (підтверджено регістрами запису `FB0Eh`/`FB01h` + `FB10h`):

```
 char# : 10 біт  →  lsb = FB01h (біти 0-7),  msb = FB0Eh (біти 8-9, bit2-7 NOT R/W)
 attr  :  7 біт  →  FB10h: bit0-2 = колір тексту, bit4-6 = колір фону (bit7 NOT R/W)
```

Діапазони № символів (спека §4): `000h`=пробіл; `001h-00Ah`="0-9"; `00Bh-024h`="A-Z";
`02Ch-04Ch`=кирилиця ROM (нетиповий порядок); `137h-13Bh`=бари батареї; `1C0h+`=**кастомний RAM-шрифт** (твоя кирилиця).
`FB11h`/`FB70h` (`bitmap_start`) ділять FONT RAM: символи `< bitmap_start` = TEXT(1bpp), `>=` = BITMAP(4bpp). Прошивка ставить `bitmap_start_lsb=80` (osd_cls) / завжди `28h` (Korth-коментар у FB11h).

## 2. Як BGMAP-адреса мапиться на клітинку екрана — ДОВЕДЕНО з asm

Апаратура **не** знає про x/y. Вона має лише лінійний 9-біт лічильник `addr` (`FB0Dh:FB00h`), який авто-інкрементується при кожному записі `data_lsb` (`FB01h`). Перенос lsb→msb апаратно **НЕ** робиться (Korth: «need manual increment on LSB-carry-outs»; підтверджено `firm_raise_bgmap_addr` ENGELS `5121` — ручний інкремент з перевіркою `jnz`).

Стрічку «клітинка → адреса» обчислює прошивка. З `AMT630A.A22` (`@@finish`, рядки `8900-8913`):

```asm
8900  mov  a,[scr_xloc]            ; X-клітинка
8901  clr  c
8902  rcr  a                       ; X/2 (бо 8px-шрифт = 2 симв/16-біт-слово)
8903  mov  r1,a
8904  mov  a,[scr_yloc]            ; Y-клітинка
8905  mov  b,(40)/2                ; STRIDE = 20 слів на рядок
8906  mul  a,b                     ; Y*20
8907  add  a,r1                    ; + X/2
8908  mov  dptr,IO_OSD_bgmap_addr_lsb
8909  movx [dptr],a                ; addr.lsb
8910  mov  a,b                     ; (старший байт множення)
8911  adc  a,0
8912  mov  dptr,IO_OSD_bgmap_addr_msb
8913  movx [dptr],a                ; addr.msb
```

> **Формула (для цієї прошивки, 8px-шрифт):** `bgmap_addr = scr_yloc*20 + scr_xloc/2`.
> Stride=20 бо вікно 0 = 40 «текстових» колонок при char_xsiz=8px, а кожне 16-біт BGMAP-слово вміщає 2 таких 8px-символи (osd_cls ставить `size_x=40/2=20`, `char_xsiz=8*2=16`).

**Для ModESP (повноцінний 16×24-шрифт)** прошивка в `diag_osd_rom_font` (`7697`) використовує **1 символ на слово**: `char_xsiz=16, size_x=20`. Тоді stride = size_x = **20 слів = 20 колонок**, формула спрощується до:

```
bgmap_addr = row * size_x + col          (для 16px-шрифту, 1 симв/слово)
```

При 200h(512) слів і stride=20 → максимум **25 рядків × 20 колонок = 500 ≤ 512**. Це і є геометрія `osd_cls`: `size_x=20, size_y=25`.

### Атрибут пишеться окремо від символу
У `@@finish` (рядок `8914-8922`) після виставлення адреси прошивка пише `FB10h (data_attr) = scr_attr` **до** запису символу. Тобто послідовність на клітинку:
`addr → (опц.) data_attr → data_msb → data_lsb (latch у VRAM + addr++)`.

## 3. Карта регістрів OSD — ТОЧНІ адреси (ENGELS `FBxx`, I²C `0x5B`)

### 3.1 Спільні регістри запису/керування

| Рег. | Ім'я (ENGELS) | Призначення | R/W нюанси |
|------|---------------|-------------|-----------|
| `FB00h` | `bgmap_addr_lsb` | BGMAP addr lsb (**auto-inc** при записі FB01h) | — |
| `FB01h` | `bgmap_data_lsb` | № символу lsb (**запис → у VRAM + addr++**) | — |
| `FB02h` | `font_addr_lsb` | FONT addr lsb (ручний аплоад) | — |
| `FB03h` | `font_data_lsb` | FONT data lsb (16-біт слово, bit0=лівий піксель) | — |
| `FB04h` | `font_data_msb` | FONT data msb | — |
| `FB05h` | `window_enable_bits` | **bit0-4=вікна 0-4 on; bit6=TEXT on/off; bit7=BITMAP/4bpp** | — |
| `FB06h` | `misc_transp_enable` | upper2bit=semitransparency ctrl | — |
| `FB0Ch` | `bright_transp_level` | upper3bit=brightness, lower3bit=transparency | — |
| `FB0Dh` | `bgmap_addr_msb` | BGMAP addr msb (**ручний** інкремент при переносі) | bit1-7 NOT R/W |
| `FB0Eh` | `bgmap_data_msb` | № символу msb (біти 8-9) | bit2-7 NOT R/W |
| `FB0Fh` | `font_addr_msb` | FONT addr msb | bit4-7 NOT R/W |
| `FB10h` | `bgmap_data_attr` | **bit0-2=колір тексту, bit4-6=колір фону** | bit7 NOT R/W |
| `FB11h` | `bitmap_start_lsb` | № першого BITMAP-символу (TEXT < нього) | — |
| `FB70h` | `bitmap_start_msb` | msb для FB11h | bit2-7 NOT R/W |
| `FB76h` | `char_xsiz` | розмір символу X у px (lower5bit, max ~24) | bit5-7 NOT R/W |
| `FB77h` | `char_ysiz` | розмір символу Y у px (lower6bit, max ~32) | bit6-7 NOT R/W |
| `FB78h` | `xyflip` | bit4 TileXflip, bit5 MapXflip, bit6 TileYflip, bit7 MapYflip | — |
| `FB89h` | `screen_position` | глобальний зсув усіх вікон (bit1=jitter!) | bit4-7 NOT R/W |

### 3.2 ПЕР-ВІКОННІ регістри — повна таблиця (точні адреси з ENGELS `321-361`)

| Поле | **Вікно 0** | **Вікно 1** | **Вікно 2** | **Вікно 3** | **Вікно 4** |
|------|:----:|:----:|:----:|:----:|:----:|
| `size_x` (ширина, симв.) | `FB07h` | `FB12h` | `FB18h` | `FB1Eh` | `FB24h` |
| `size_y` (висота, симв.) | `FB08h` | `FB13h` | `FB19h` | `FB1Fh` | `FB25h` |
| `xyloc_msb` | `FB09h` | `FB14h` | `FB1Ah` | `FB20h` | `FB26h` |
| `xloc_lsb` | `FB0Ah` | `FB15h` | `FB1Bh` | `FB21h` | `FB27h` |
| `yloc_lsb` | `FB0Bh` | `FB16h` | `FB1Ch` | `FB22h` | `FB28h` |
| `vramaddr_lsb` | **немає** (фікс=000h) | `FB17h` | `FB1Dh` | `FB23h` | `FB29h` |

Геометрія блоку очевидна: вікно 0 = 5 байт (`FB07h-FB0Bh`, без vramaddr), вікна 1-4 = по 6 байт поспіль.

**`xyloc_msb` (один байт на вікно)** упаковує старші біти кількох полів. ENGELS коментує (`FB14h`): «MSBs for xloc, yloc, vramaddr (plus 1bit unknown)». Точне розкладання бітів реверсу до кінця не дано, АЛЕ asm `diag_draw_bitmap_width_height` (AMT630A `9549-9553`) показує мапінг **bgmap-addr.msb → window_N_xyloc_msb.bit7**:

```asm
9545  mov  dptr,IO_OSD_bgmap_addr_lsb
9547  mov  dptr,IO_OSD_window_2_vramaddr_lsb   ; vramaddr.lsb = bgmap_addr.lsb
9549  mov  dptr,IO_OSD_bgmap_addr_msb
9551  ror  a                                   ; addr.msb → bit7
9552  mov  dptr,IO_OSD_window_2_xyloc_msb       ; vramaddr.msb (9-й біт) у bit7
```

> **Висновок про vramaddr:** адреса BGMAP-вікна = 9 біт: `vramaddr_lsb` (8 біт, `FB17h/1Dh/23h/29h`) + старший біт у `xyloc_msb.bit7`. Це дозволяє показати кожне вікно з **довільної ділянки BGMAP** (512 слів = рівно 9-біт адресний простір → збігається!).

**Координати xloc/yloc:** 11-біт (lsb у `FB0Ah/0Bh`, старші біти в `xyloc_msb`). Базове зміщення: `xloc=10` = крайня ліва, `yloc=12` = крайня верхня (спека; підтверджено `osd_cls` `xloc=10+0`, `yloc=12+20`).

### 3.3 Масштаб (FB32/33/34) + субпіксельний scale

| Рег. | Ім'я | Вікна | Формат |
|------|------|-------|--------|
| `FB32h` | `window_0_scale` | вікно 0 | bit0-1=ScaleX, bit2-3=ScaleY (×1/×2/×3/×4)  • bit4-7 NOT R/W |
| `FB33h` | `window_1_and_2_scale` | вікна 1,2 | 2×2bit: lsbs=ScaleX, msbs=ScaleY (по вікну) |
| `FB34h` | `window_3_and_4_scale` | вікна 3,4 | те саме |
| `FB2Bh-FB2Eh` | `window_0_vscale_*` | вікно 0 | по-рядковий vscale (для 24/32-лінійних символів), 00h/FFh-заповнення |
| `FB2Fh-FB31h` | `window_0_hscale_*` | вікно 0 | по-піксельний hscale |

> ENGELS коментар FB33h: «txt.scale (2x2bit, for lsbs=ScaleX and msbs=ScaleY, per window?)». Init-список (AMT630A `3943-3945`) виставляє всі три у `00h` (×1).

### 3.4 Розмір символу FB76/FB77 — поведінка з asm-експериментів Korth
AMT630A `6868-6875` (коментарі дизасемблера):
- `char_xsiz=16` — норм; `=12` норм; `=24` норм; `=1` — «draws ONLY 1-PIX vertically per 16bit write»; `=8` — «goes crap diagonally: CHAR 0 overlaps CHAR 1 → fix: use only CHAR 0 and CHAR 2» (тобто при 8px треба stride/2, як у `osd_cls`).
- `char_ysiz=24` при 8px-сітці теж даё «crap diagonally».

> **Практика для ModESP:** використовуй `char_xsiz=16, char_ysiz=24` (повний 16×22/16×24 ROM-розмір) → 1 символ на BGMAP-слово, stride=size_x, без overlap-граблів.

### 3.5 Палітра (FB56h-FB61h) — фактичні фабричні значення (ENGELS `377-388`)

| № | msb / lsb | Колір (RGB 4:4:4) |
|---|-----------|-------------------|
| 0 | — фікс | прозорий (видно відео / синій No-Signal фон) |
| 1 | `FB56h`=00h / `FB57h`=0Fh | червоний |
| 2 | `FB58h`=00h / `FB59h`=F0h | зелений |
| 3 | `FB5Ah`=0Fh / `FB5Bh`=00h | синій |
| 4 | `FB5Ch`=00h / `FB5Dh`=FFh | жовтий |
| 5 | `FB5Eh`=0Fh / `FB5Fh`=F0h | блакитний |
| 6 | `FB60h`=0Fh / `FB61h`=FFh | білий |
| 7 | — фікс | чорний |

Формат (спека §6): lsb bit0-3=Red, bit4-7=Green; msb bit0-3=Blue (0-10, 11-15=max).
> ⚠ Korth позначає ці регістри «fixed» — у деяких прошивках вони фактично hardcoded і запис по I²C може ігноруватись. **Перевір на бенчі.**

## 4. Регістр FB05h (enable) — детально

```
bit0 = Window 0 ON      bit4 = Window 4 ON
bit1 = Window 1 ON      bit5 = (?)  ; ENGELS: «used other bits=?»
bit2 = Window 2 ON      bit6 = TEXT ON/OFF (глобально ховає вікна)  ; AA77: «clear bit6»
bit3 = Window 3 ON      bit7 = BITMAP / 4bpp режим                   ; AA7E: «set bit7»
```

ENGELS `AA73-AA89` показує живе керування bit6/bit7. Fizik і `osd_cls` ставлять `FB05h=0x01` (лише вікно 0), Fizik `initDisplay` — `0x1F` (всі 5 вікон).

> **Glitch при записі FONT:** обнуляй `FB05h=0x00` на час аплоаду шрифту (спека §7; підтверджено AMT630A `9514-9517`: «DISABLE WINDOWS (somewhat required)… otherwise a FEW FONT writes are randomly GARBLED»).

## 5. Канонічна послідовність налаштування вікна 0 (з asm)

`osd_cls` (AMT630A `5938-5959`) — еталонний 8px-варіант:

```asm
FB07h(size_x)    = 40/2 = 20      ; 20 BGMAP-слів/рядок
FB08h(size_y)    = 25             ; 25 рядків  (20*25=500 ≤ 512)
FB09h(xyloc_msb) = 0
FB0Ah(xloc_lsb)  = 10  (+0)       ; ліва межа
FB0Bh(yloc_lsb)  = 12  (+20)      ; верхня межа +зсув
FB76h(char_xsiz) = 8*2 = 16
FB77h(char_ysiz) = 8
FB11h(bmp_start) = 80
FB05h(enable)    = 01h            ; лише вікно 0
```

Повнорозмірний 16×24-варіант (`diag_osd_rom_font` `7697-7706`):

```asm
FB07h=20  FB08h=8  FB09h=0  FB0Ah=10  FB0Bh=30
FB76h=16  FB77h=24  FB05h=01h  scr_attr=47h   ; bg=4(жовт), fg=7(чорн)
```

Fizik (доведено по I²C, `AMT630.h::osdPrint`): `0x05=0x01; 0x07=len; 0x08=1; 0x76=16; 0x77=22; 0x09=0; 0x0A=x; 0x0B=y; 0x0D=0; 0x00=0; (per char) 0x0E=0; 0x01=code; 0x10=0x09`.

## 6. Init-послідовність OSD-залізі (AMT630A `init_OSD_hardware` + `init_osd_io_list`)

Прошивка при старті:
1. `init_io_via_io_list(init_osd_io_list)` — записує дефолти у весь блок `FB05h…FB61h` (порядок у списку = §3 init list).
2. Чистить BGMAP: для `addr.msb=0..1`, `addr.lsb=0..255` пише `data=01C0h` (порожній символ RAM-шрифту) + `attr=12h`. **512 слів** (`3864-3882`).
3. Залишає `font_addr` обнуленим.

`init_osd_io_list` дефолти, що варто знати: `bright_transp_level=80h`, `char_xsiz=char_ysiz=08h`, всі size/loc=0, scale=0, палітра 1-6 = табл. §3.5.

## 7. Пріоритети / шарування 5 вікон

- **Вікно 0** — найвищий пріоритет (малюється поверх), BGMAP-addr **фіксована = 000h**, немає `vramaddr`. Прошивка тримає на ньому головне меню/статус.
- **Вікна 1-4** — нижчий пріоритет у порядку спадання (1>2>3>4), кожне з власним `vramaddr_lsb` (9-біт) → можуть дивитись на **різні** ділянки одного BGMAP.
- Прозорий колір 0 у клітинці = крізь нього видно нижче вікно / живе відео (тому overlay не закриває картинку повністю).
- `FB06h`/`FB0Ch` — глобальна напівпрозорість (text/bg + рівень) для ефекту «текст поверх відео».

> Реверс не дав явного per-window z-order регістру — пріоритет визначається **номером вікна** (фіксований у залізі). Це узгоджено між спекою та логікою фіксованого вікна 0.

## 8. СТРАТЕГІЯ розкладки: меню ModESP + overlay-сповіщення одночасно

### 8.1 Розподіл BGMAP (512 слів, stride=20, 16×24-шрифт, 1 симв/слово)

| Ділянка BGMAP | Слова | Призначення | Вікно |
|---------------|-------|-------------|-------|
| `000h-1F3h` | 0…499 | **Головне меню ModESP** (20×25 сітка; реально 20 кол × ~16-25 рядків) | **Вікно 0** (addr=000h фікс) |
| (overlay живе в ТОМУ Ж BGMAP, але вікна 1-4 дивляться на хвіст) | | | |

> Проблема: BGMAP лише 512 слів і вікно 0 з'їдає majority. Для overlay є два підходи:

**Підхід A — overlay у хвості BGMAP (рекомендований).**
Зменш робочу зону меню до, напр., 20×22=440 слів (`000h-1B7h`). Хвіст `1B8h-1FFh` (72 слова) віддай під overlay-банер. Вікно 1: `vramaddr=1B8h`, `size_x=20, size_y=3`, `yloc` внизу екрана. Меню — вікно 0; банер сповіщення — вікно 1 (нижчий пріоритет, але розташований у вільній зоні екрана, тож не конфліктує позиційно).

**Підхід B — overlay тим самим вікном 0, але інша Y-зона.**
Меню займає рядки 0-19, рядки 20-24 (адреси `190h-1F3h`) — зона сповіщень. Один прохід запису, без другого вікна. Простіше, але overlay не може «спливати» поверх меню — лише в окремому рядку.

**Підхід C — overlay як спрайт поверх (для важливих ALARM).**
Вікно 1 з власним `vramaddr` на маленький блок (напр. 16×3=48 слів у хвості), розміщене **поверх** центру меню через `xloc/yloc`, на ×2 scale (`FB33h`), яскравий фон (attr bg=1 червоний). Вмикається лише на час тривоги бітом `FB05h.bit1`; меню (вікно 0) лишається під ним. **АЛЕ:** вікно 0 має вищий пріоритет → overlay-вікно 1 буде ПІД меню. Щоб overlay був ЗВЕРХУ — клади меню у вікно 1+, а overlay у вікно 0 (фіксований addr 000h). Тобто:

> **Найкраща схема для KOZHAN:**
> - **Вікно 0** (пріоритет №1, addr=000h) = **OVERLAY/ALARM** банер. Зазвичай `FB05h.bit0=0` (вимкнено). При сповіщенні — пишеш текст у addr 000h+ і вмикаєш bit0. З'являється поверх усього.
> - **Вікно 1** (`vramaddr` напр. 040h) = **повне меню ModESP**. Завжди `FB05h.bit1=1`.
> - Решта вікон 2-4 — резерв (графіки сигналу, бари батареї, RSSI-індикатор).

### 8.2 Інтеграція з наявним ModESP `IDisplayRenderer`
`MenuEngine` формує `DisplayFrame` (4 рядки × 40 байт UTF-8, `renderer.h`). Новий `Amt630aRenderer : IDisplayRenderer`:
- `init()` — I²C-послідовність §5/§6 (вибір входу, палітра, char 16×24, enable вікна меню).
- `render(frame)` — для кожного рядка: `osd_print(bgmap_addr_меню, utf8→charcode, attr)`. UTF-8→№символу через `osd_charmap.h` (кирилиця у RAM-шрифт `1C0h+`).
- Тримай тіньовий буфер у RAM ESP32 (BGMAP **не читається** назад) і пиши лише змінені клітинки (diff), щоб мінімізувати I²C-трафік.
- Overlay-API: окремий метод `notify(text, level)` → пише у вікно 0 (addr 000h) + `FB05h |= bit0`; таймаут → `FB05h &= ~bit0`.

> `DisplayFrame::MAX_ROWS=4` замало для повного TFT-меню — для AMT630A варто розширити кадр (напр. `MAX_ROWS=16`, `MAX_BYTES` під 20 колонок×UTF-8). Це зміна в `renderer.h` під AMT630A-профіль.

## 9. Конфлікти / невирішене між джерелами

1. **FE2Ah (детект сигналу) — РОЗБІЖНІСТЬ:**
   - User-спека §3: `bit4`=сигнал на **вибраному** вході, `bit6`=на **невибраному**.
   - ENGELS `729`: `bit4 = HaveCVBS1`, `bit6 = HaveCVBS3` (тобто **per-input**, не selected/unselected). + bit0-3 = ErrorFlags.
   - → Імовірно правий ENGELS (per-фізичний-вхід). **Перевірити на бенчі.**
2. **xyloc_msb бітова розкладка** — реверс дає лише `bit7=vramaddr-msb` (доведено asm) + «MSBs for xloc,yloc,+1 unknown bit» (Korth-коментар, не розкладено по бітах). Точне положення старших бітів xloc/yloc у цьому байті **не задокументовано** — встановлювати емпірично.
3. **Палітра FB56h-FB61h «fixed»** — Korth позначає як hardcoded; невідомо, чи приймає запис по I²C на цільовій прошивці. Спека ж описує як програмовані. **Перевірити запис кольорів на бенчі.**
4. **Stride/розмір вікна = 8px vs 16px** — обидві прошивки (ENGELS OEM, AMT630A nocash) ганяють **8px-шрифт** (2 симв/слово, stride=20), а не 16×22. ModESP хоче 16×24 (1 симв/слово). Геометрія 16px-режиму взята з `diag_osd_rom_font` (тестова, не основна gui-петля) — потребує підтвердження, що основний рендер-конвеєр стабільний при `char_xsiz=16` на цільовій платі.
5. **FB05h.bit5** — призначення невідоме (ENGELS: «used other bits=?»). Не чіпати.
6. **Banks LCD у Fizik** — Fizik `0x58`=LCD-рег (`TFT_LCD_REG`), але спека §2 каже `0x58`=Global, а LCD/Tcon=`0x5C`. Для OSD це неважливо (OSD завжди `0x5B`), але при копіюванні Fizik-init врахуй: його «LCD»-записи йдуть у Global-банк.

## 10. Швидкий чек-ліст реалізації (Шлях A, I²C `0x5B`)

```
1. (раз) init: char_xsiz=16, char_ysiz=24; палітра (якщо приймає); bitmap_start.
2. (раз) FB05h=0 → залити кирилицю у FONT RAM 1C0h+ (FB02/0F addr, FB04→FB03 data) → FB05h назад.
3. Вікно МЕНЮ: size_x=20, size_y=N, xloc=10, yloc=12, vramaddr=040h, enable bit.
4. Вікно OVERLAY (вікно 0): addr фікс 000h, size під банер, enable bit0 лише при тривозі.
5. render(): diff проти тіні → osd_print(addr, code, attr); addr.lsb auto-inc, msb вручну при переносі 8-біт.
```
