# `at7456e` — OSD overlay on composite video (SPI)

> 📖 **In Ukrainian:** [.../uk/.../at7456e](../../../uk/03-framework-reference/drivers/at7456e.md)

Display backend for the AT7456E chip (MAX7456-compatible) — an OSD character
overlay on top of composite (CVBS) video. The driver provides the **`display`**
capability through the `IDisplayPort` semantic seam (see
[ADR-002](../../../../docs/display/ADR-002-display-architecture.md)) — a sibling
of `amt630a`. The `display` module pushes semantic Views into it
(`present_main`/`present_menu`/`present_notice`), and all layout (scrolling,
cursor, centering, mapping to NVM-font glyphs) is encapsulated inside the driver.

**A capability, not a driver.** Per
[R0.1](../rules.md#r01--роль--здатність-capability-ніколи-не-драйвер),
the display is a `display` capability that the module consumes without knowing the
chip. `display` is a singleton in the system, so instead of bindings.json the
backend is selected via the Kconfig `choice`
(see [ADR-002 §2](../../../../docs/display/ADR-002-display-architecture.md), the
"NO registry" decision). The `display` module has no `#include` of a concrete
port — it receives the chosen `IDisplayPort*` via DI.

> ⚠️ **Note:** this driver's pins are read from **Kconfig**, not from
> `board.json`. This is a temporary exception (other drivers take their
> peripherals from board.json) until an `spi_displays` section appears in
> board.json (roadmap Phase 3). Until then the driver compiles, but binding it
> via board.json/bindings.json is **not possible**.

## Capability and channels

| Field | Value |
|------|----------|
| `category` | `display` |
| `hardware_type` | `spi_display` |
| `transport` | `wired` |
| `provides.capability` | `display` |
| `provides.type` | `display` |

The `display` capability **has no channels** in the sensor/actuator sense — the
driver publishes no state keys to SharedState. It consumes semantic Views from the
`display` module and renders them on screen. Contrast with the sensor
`ble_xiaomi_th`, where one device provides several channels
(`temperature`/`humidity`/`battery`) — for `display` there is no such split.

## Bindings

`display` is a singleton, so binding goes **not through bindings.json**, but
through the Kconfig backend selection and pins. In `idf.py menuconfig`:

1. Enable the driver: **ModESP Drivers → AT7456E** (`CONFIG_MODESP_DRIVER_AT7456E`).
2. Set the pins and video parameters in the **AT7456E driver (pins/video)** menu.

Or directly in `sdkconfig.defaults`:

```
CONFIG_MODESP_DRIVER_AT7456E=y
CONFIG_MODESP_DISPLAY_AT7456E_CS=5
CONFIG_MODESP_DISPLAY_AT7456E_MOSI=23
CONFIG_MODESP_DISPLAY_AT7456E_CLK=18
CONFIG_MODESP_DISPLAY_AT7456E_MISO=19
CONFIG_MODESP_DISPLAY_AT7456E_PAL=y
CONFIG_MODESP_DISPLAY_AT7456E_SYNC_AUTO=y
```

Backend registration is a single point in `drivers/at7456e/src/at7456e_port.cpp:134`:

```cpp
MODESP_REGISTER_DISPLAY(at7456e, &at7456e_factory)
```

The factory returns a singleton `At7456ePort` (zero-heap); `Binding`/`HAL` are
not used — the backend is chosen precisely by the Kconfig selection, not by a
board.json string.

## Settings

The manifest has no `settings` section — all parameters are set through Kconfig
(`drivers/at7456e/Kconfig`):

| Kconfig | Description | Default |
|---------|------|------------------|
| `MODESP_DISPLAY_AT7456E_CS` | CS line GPIO | `5` |
| `MODESP_DISPLAY_AT7456E_MOSI` | DATA/MOSI line GPIO | `23` |
| `MODESP_DISPLAY_AT7456E_CLK` | CLK line GPIO | `18` |
| `MODESP_DISPLAY_AT7456E_MISO` | MISO line GPIO | `19` |
| `MODESP_DISPLAY_AT7456E_STD` | Video standard: `PAL` (16 rows) / `NTSC` (13 rows) | `PAL` |
| `MODESP_DISPLAY_AT7456E_SYNC` | Sync source: `auto` / `internal` / `external` | `auto` |

Sync source: `internal` — own sync (screen lights up without input video);
`auto` — internal only when input sync is lost; `external` — hold the input sync.

## Protocol and hardware

| Parameter | Value |
|----------|----------|
| Chip | AT7456E (MAX7456-compatible) |
| Interface | SPI, **bit-bang** (4 GPIO: CS/MOSI/CLK/MISO) |
| Output | OSD character overlay on top of CVBS video |
| Grid (PAL) | 30 × 16 characters |
| Grid (NTSC) | 30 × 13 characters |
| Cyrillic font | loaded into the chip's character NVM |

The driver talks to the chip over MAX7456 registers (`VM0`, `DMM`, `DMDI`, …),
forming SPI frames itself by GPIO "toggling" (`shift_out`/`shift_in`,
`at7456e.cpp:54-89`). The chip's presence is verified by an echo test of the
`DMAL` register (`present()`, `at7456e.cpp:122`); if the chip does not respond,
the port is disabled and the system keeps running (`init()` returns `false`,
`at7456e_port.cpp:55`).

**Cyrillic font in NVM.** Glyphs are uploaded into the chip's character NVM once
(`upload_font`, `at7456e.cpp:208`). To avoid wearing out the NVM with repeated
writes, a sentinel guard is used: if the font is already present (a byte match at
the sentinel address), the upload is skipped. The UTF-8 → NVM glyph index mapping
lives in `osd_charmap` (a layout specific to this chip, not shared with other
displays).
