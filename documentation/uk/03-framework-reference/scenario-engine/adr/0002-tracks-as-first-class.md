# ADR-0002: Доріжки як first-class-концепція (а не дороблення згодом)

> 📖 **In English:** [documentation/en/03-framework-reference/scenario-engine/adr/0002-tracks-as-first-class.md](../../../../en/03-framework-reference/scenario-engine/adr/0002-tracks-as-first-class.md)

**Статус:** Прийнято
**Дата:** 2026-05-02

## Контекст

Sequence Engine виконує фазові timeline-сценарії. Початкове обговорення розглядало односмугові сценарії (одна послідовність фаз) як базу, з потенційним додаванням підтримки мультидоріжок пізніше.

Реальна вбудована автоматизація **завжди мультиканальна** — приклад рецепта мультиварки:
- Track 1 (керування нагрівом): warmup → simmer → finish
- Track 2 (графік помішування): активно 10 хв → idle до завершення нагріву
- Track 3 (сповіщення UI): notify_at_minute_20 → notify_done
- Track 4 (safety monitor): безперервне виявлення несправностей

Паралельні доріжки поділяють timeline сценарію, але мають незалежне просування фаз. Без first-class-підтримки доріжок автори рецептів забезпечують паралелізм вручну через cross-module-хаки.

Аналогія користувача (MIDI / перфокарта) — точна метафора: сценарій = пісня з кількома доріжками, що грають одночасно, синхронізованими спільною часовою лінією.

## Рішення

**Доріжки — first-class-концепція в scenario engine починаючи зі Stage 1.**

Конкретно:
- Заголовок `.modr` має поле `track_count` (1..6, `MAX_TRACKS_PER_SCENARIO`)
- Кожна доріжка має власний масив фаз, переходів, поточний стан
- Один tick-таск ітерує екземпляри × доріжки; стан-машини кожної доріжки виконуються незалежно
- `completion_rule` (`all_tracks_complete` | `any_track_complete` | `main_track_complete`) визначає завершення сценарію
- Односмуговий рецепт = `tracks: [{name: "main", phases: [...]}]` — вироджений випадок мультидоріжкового
- Синхронізація між доріжками через SharedState (патерн publish/subscribe, існуюча інфраструктура ModESP)

**НЕ відкладати до Stage 1.5**, бо вартість retrofit-у висока — концепція доріжок змінює бінарний формат, API, структуру стан-машини, layout NVS. Закладати tracks-aware з першого дня значно дешевше.

## Розглянуті альтернативи

### A. Односмуговий MVP, мультидоріжки на Stage 1.5 — відхилено

**Переваги:**
- Менший MVP (~30% менше коду)
- Простіше міркувати на ранніх етапах

**Недоліки (чому відхилено):**
- Потрібна breaking-зміна бінарного формату для додавання доріжок
- Breaking-зміна API (`engine.track_state(handle)` → `engine.track_state(handle, track)`)
- Зміна layout NVS (sub-state кожної доріжки відсутній у токенах односмугового варіанта)
- Реструктуризація стан-машини
- Автори рецептів реалізують мультипроцесну логіку через односмуговий + workaround «стан-машина в ключах стану» в міжчассі → технічний борг
- Користувач явно попросив доріжки «з самого початку»

### B. HSM (ієрархічні стан-машини) замість плоских доріжок — відхилено

**Переваги:**
- Стандартний формалізм індустрії (Samek QP, BOOST.MSM, ETL state_chart)
- Ортогональні регіони формально підтримують concurrency

**Недоліки (чому відхилено):**
- Overkill для здебільшого лінійних рецептів з епізодичним розгалуженням
- Накладні витрати реалізації ієрархії HSM (~3× коду)
- Когнітивне навантаження на автора рецепта (state regions, пріоритет пошуку переходів)
- IEC 61131-3 SFC і ISA-88 — обидва плоскі списки фаз з паралельними гілками, не HSM
- BehaviorTree.CPP теж відмовився від HSM на користь плоских композиційних дерев

### C. Behavior trees замість списків фаз — відхилено

**Переваги:**
- Композиційніше (піддерева перевикористовуються)
- ROS 2 Nav2 у продакшені валідує підхід

**Недоліки (чому відхилено):**
- Автори рецептів — не робототехніки; список фаз — доступніша ментальна модель
- Авторинг дерев без візуального редактора (який поза скоупом рушія) — болісний у JSON
- Мультидоріжки паралельно = паралельні гілки SFC, простіше

## Наслідки

### Позитивні
- Реальні рецепти природно виражають мультипроцесну автоматизацію (мультиварка, ферментер, лабораторний batch)
- Sync між доріжками через SharedState перевикористовує існуючу інфраструктуру (без нового IPC)
- API узгоджене з ментальною моделлю MIDI/sequencer
- Узгодження з ISA-88 / SFC збережено
- Аналогія користувача з перфокартою підтримана елегантно

### Негативні
- Більший скоуп MVP (~3000 LOC проти ~2200)
- Семантика sync між доріжками потребує ретельної документації (ADR-0003)
- Більше стану для відстеження в RAM рушія і NVS
- Per-track UI mirror keys відкладені до Stage 1.5 (обмеження місткості)

### Нейтральні
- Масиви фіксованої місткості (`MAX_TRACKS_PER_SCENARIO = 6`) задають жорсткий верхній ліміт — Kconfig'ується за потреби

## Посилання

- Foundation document уже згадує доріжки (розділ 4.5, декомпозиція фаз + concurrent behaviors)
- Індустрія: ROS Smach Concurrence container, BehaviorTree.CPP `Parallel` node, MIDI sequencer model
- IEC 61131-3 SFC, паралельні гілки
- План Q1 (таблиця доріжок у бінарному форматі), Q2 (методи API per-track)

## Тригери для перегляду

Переглянути, якщо:
- Усі реальні рецепти виявляться односмуговими → прийняти overhead, але задокументувати доріжки як невикористовувану функцію Stage 2
- Sync між доріжками виявиться надто заплутаним → спростити до семантики «сценарій пише лише в main track»
- Прорив бюджету пам'яті → зменшити `MAX_TRACKS_PER_SCENARIO` до 4
