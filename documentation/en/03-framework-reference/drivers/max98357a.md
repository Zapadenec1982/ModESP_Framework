# `max98357a` — I²S Class-D amplifier (audio output)

> 📖 **In Ukrainian:** [.../uk/.../max98357a](../../../uk/03-framework-reference/drivers/max98357a.md)

Audio output driver for the MAX98357A — a mono Class-D amplifier with a built-in I²S
DAC. It provides the `audio` capability through the
[`IAudioSink`](../../../../components/modesp_hal/include/modesp/hal/audio_sink.h)
interface: it owns the I²S TX channel, DMA and the SD/shutdown pin (hardware mute) and
does exactly one thing — move ready-made 16-bit mono PCM to the speaker. Clips, decoding,
tones and volume are unknown to it — that is the job of the `player` module, which
generates/decodes PCM and hands it to `write()`.

**Role = capability (R0.1).** The `player` module declares the role `audio_main` with
capability `capability: "audio"` and never knows which driver provides it. Today it is
`max98357a` over the wire (I²S); tomorrow it could be another codec or a future
transport — the module does not change. The driver registers as `audio` with
`hardware_type: i2s_bus`, `transport: wired`, `requires_address: false`.

Audio output is a **singleton**: exactly one sink, driven by a single playback task
inside `player`. So the factory builds one static instance (zero-heap), and all sink
methods are called from that same task sequentially — there are no races for the I²S
channel.

REQUIRES: `modesp_hal`. The driver is compiled only when
`CONFIG_MODESP_DRIVER_MAX98357A` is enabled (generated toggle in the "ModESP Drivers"
menu).

## Capability and channels

| Attribute | Value |
|---------|----------|
| `capability` | `audio` (consumed by the `player` module as `audio_main`) |
| Direction | output (sink) |
| `hardware_type` | `i2s_bus` (wired I²S bus from board.json) |
| `transport` | `wired` |
| `requires_address` | `false` (one amplifier per I²S bus) |
| `multiple_per_bus` | `false` |

One `i2s_buses` entry in board.json → one audio output. Channels are not multiplexed
by `address` (unlike BLE sensors): the MAX98357A is mono, one bus = one speaker.
The PCM format is fixed by the interface: 16-bit signed mono; the sample rate is
set by `player` when the stream starts (`start(sample_rate_hz)`), defaulting to the
`sample_rate_hz` from board.json.

## Bindings

### board.json

The I²S bus is declared in the `i2s_buses` section. The BCLK/WS/DOUT pins are required;
`sd` is the hardware mute pin (SD/shutdown), `-1` if the amplifier is pulled to "on" in
hardware. `sample_rate_hz` is the default rate (16000 is enough for alarm tones).

```json
"i2s_buses": [
  { "id": "i2s_0", "bclk": 15, "ws": 16, "dout": 7, "sd": 17, "sample_rate_hz": 16000 }
]
```

### bindings.json

One `hardware` binding (the I²S bus) to the `max98357a` driver, role `audio_main`,
module `player`:

```json
[
  { "hardware": "i2s_0", "driver": "max98357a", "role": "audio_main", "module": "player" }
]
```

The `audio_main` role is owned by the `player` module (R1.2), so `module` must be
`player`. The role label does not mention the transport (R1.3): "Audio output", not
"I²S speaker".

## Settings

The manifest declares no binding settings (`"settings": []`). All hardware
configuration comes from the `i2s_buses` entry in board.json (pins +
`sample_rate_hz` + mute pin), not from bindings.json. The driver is deliberately
minimal: volume is applied by `player` in software (`caps().hw_volume ==
false`), and the queue/priority/decoding also live in the module.

## Hardware notes

- **Responsibility split.** The HAL stores only the I²S bus config (pins + rate + SD pin).
  The `i2s_chan_handle_t` itself, the DMA buffers and channel enablement belong to the
  driver — the HAL does not depend on `driver/i2s_std.h`. The driver acquires the
  resource via `hal.find_i2s_bus(hardware_id)`.
- **Hardware mute.** The SD pin controls the amplifier: HIGH = sound, LOW = off.
  The driver holds SD LOW at rest (`init()`/`stop()`) and raises it only for the
  duration of a stream (`start()` unmutes, `stop()` restores). If SD is pulled in
  hardware, set `sd: -1` — pin control is skipped.
- **Master mode.** The driver configures I²S in Philips slot mode, 16-bit, mono, with
  the ESP32 as master (generating BCLK/WS). MCLK is not used.
- **Degrade without crashing.** If `init()` returns `false` (no bus in
  board.json, an I²S error), audio is simply disabled — the system lives on. The
  `audio_main` role in `player` is marked `optional: true`.

## Common pitfalls

**No bus in board.json.** If the `hardware` in the binding does not match any
`id` in `i2s_buses`, the factory logs `no i2s bus '<id>'` and returns `nullptr` — audio
does not work. Cross-check `hardware` in bindings.json against `id` in board.json.

**Driver disabled in menuconfig.** The board binds `max98357a`, but
`CONFIG_MODESP_DRIVER_MAX98357A` is disabled → the build fails FATAL. Reconcile with:
`python tools/drivers_sync.py --fix`.

**Silence despite "Playing".** Check the SD pin: if it is physically disconnected or
pulled LOW, the amplifier stays muted. For an always-on module, set `sd: -1`.
