# ADR-0001: Бінарний формат `.modr` у LittleFS, а НЕ C++ constexpr

> 📖 **In English:** [documentation/en/03-framework-reference/scenario-engine/adr/0001-binary-format-not-constexpr.md](../../../../en/03-framework-reference/scenario-engine/adr/0001-binary-format-not-constexpr.md)

**Статус:** Прийнято
**Дата:** 2026-05-02

## Контекст

Sequence Engine у ModESP_v4 виконує «recipes» — фазові timeline-сценарії з доріжками, переходами, параметрами. Рецепти можуть постачатися з прошивкою (OEM-shipped) або потенційно бути OTA-завантажуваними (Stage 1.5+). Їх треба ефективно завантажити на пристрій, валідувати і виконувати без накладних витрат на runtime-парсинг.

Дві основні альтернативи:

**A. Бінарний блоб `.modr` у LittleFS:** compile-time-інструмент генерує запакований бінарник; runtime-завантажувач парсить у буфер фіксованого розміру; рушій виконує з RAM.

**B. Масиви C++ constexpr-структур:** compile-time-інструмент генерує заголовки `<recipe>_data.h` з constexpr-масивами; рушій посилається на них прямо у flash без runtime-парсингу.

Промислове використання ESPHome демонструє, що підхід B працює на масштабі. Foundation document, розділ 4.4, специфікує підхід A (бінарний блоб).

## Рішення

**Підхід A — бінарний `.modr` у LittleFS** для Stage 1 MVP.

Конкретно:
- `compile_scenario.py` генерує `data/scenarios/<recipe_name>.modr` (один файл на рецепт)
- Образ партиції LittleFS пакує `data/`
- Runtime: рушій `f_read` весь блоб у буфер фіксованого розміру (`MODR_MAX_SIZE = 16 KB`)
- Завантажувач валідує magic + version + CRC32 + структуру; розв'язує хеші дій/умов
- Рушій виконує з RAM-буфера

**Constexpr-шлях відкладається** до Stage 1.5 для factory-рецептів, якщо/коли з'являться конкретні вигоди.

## Розглянуті альтернативи

### B (constexpr) — відхилено для MVP

**Переваги:**
- Менший footprint у flash (без накладних витрат LittleFS, без коду парсера)
- Швидше завантаження (без I/O на load)
- Без поверхні для fuzzing (немає runtime-парсера)
- Перевірено в індустрії (ESPHome у продакшені)
- Простіший бюджет пам'яті

**Недоліки (чому відхилено):**
- **Рецепт лише як артефакт прошивки:** будь-яка зміна рецепта вимагає перебудови прошивки. Foundation document явно обрав бінарний шлях заради interop, AI-friendly tooling, майбутніх OTA-завантажуваних рецептів.
- **Інтеграція з пайплайном маніфестів слабша:** constexpr-emit вимагає окремого інструмента генерації заголовків зі знаннями C++, а не просто JSON-to-binary.
- **OTA-рецепти Stage 1.5** стають несумісними без перебудови.

### Гібрид (constexpr factory + binary OTA) — відкладено

Розглянуто. Додає складності (два шляхи коду в рушії для зберігання рецепта). MVP залишає один шлях. Розширення Stage 1.5, якщо рецепти з cloud push стануть реальною функцією продукту.

## Наслідки

### Позитивні
- Виконано мандат Foundation document — авторинг у JSON + бінарний runtime
- Дружнє до інструментарію (`compile_scenario.py` центральний, `scenario_schema.json` зрозумілий людині)
- Шлях до OTA-завантажуваних рецептів очевидний
- AI-friendly авторинг (LLM можуть генерувати JSON-маніфести)

### Негативні
- Завантажувач — поверхня атаки — **пом'якшення: інтеграція libFuzzer на Step 8** (60 с чистого прогону в CI, ~5 хв розширеного локально)
- 16 КБ статичного буфера на завантажений сценарій (~64 КБ у гіршому випадку з 4 екземплярами; бюджетовано)
- Завантаження повільніше за constexpr (~1–2 мс читання з LittleFS; нерелевантно)
- Потрібне версіонування схеми (поле `format_version` у заголовку, міграції на breaking changes)

### Нейтральні
- Узгодження з розділом 4.4 Foundation document збережено
- Шлях розширення Stage 1.5 чіткий (додати constexpr-альтернативу для factory-рецептів; обидва шляхи співіснують у рушії)

## Посилання

- Foundation document, розділ 4.4 («Authoring vs runtime format»)
- Індустріальне дослідження: compile-time YAML-підхід ESPHome (constexpr-альтернатива)
- План Q1 (специфікація бінарного формату)
- Step 8 (пом'якшення через інтеграцію libFuzzer)
- Поставка Stage 1.5: гібридне зберігання рецептів

## Тригери для перегляду

Переглянути, якщо:
- У завантажувачі під час фаззингу спливе баг рівня CVE → можливий перехід виключно на constexpr-шлях
- Cloud-push-рецепти Stage 1.5 виявляться непотрібними (наприклад, усі OEM-рецепти запікаються в прошивку) → constexpr стає простішим вибором
- Тиск пам'яті змусить ущільнити footprint сильніше, ніж дозволяє 16 КБ блоб
