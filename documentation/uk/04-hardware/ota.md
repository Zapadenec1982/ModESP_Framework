# OTA — оновлення прошивки через ефір

> 📖 **In English:** [documentation/en/04-hardware/ota.md](../../en/04-hardware/ota.md)

ModESP v4 підтримує автоматичні оновлення прошивки через ефір із
автоматичним відкатом, якщо новий образ не запустився. Побудовано на
основі `esp_https_ota` з ESP-IDF та схеми з двома розділами додатка.

ВИМАГАЄ: flash 4 МБ+, розділи, налаштовані для OTA (стандартний
`partitions.csv` містить і розділи додатка, і розділи даних).

## Розмітка розділів

```
Name        Type    SubType   Offset    Size
nvs         data    nvs       0x9000    0x6000     (24 KB)
otadata     data    ota       0xF000    0x2000     (8 KB)
phy_init    data    phy       0x11000   0x1000     (4 KB)
ota_0       app     ota_0     0x20000   0x1E0000   (1.875 MB)
ota_1       app     ota_1     0x200000  0x1E0000   (1.875 MB)
littlefs    data    spiffs    0x3E0000  0x20000    (128 KB)
```

Два слоти `ota_*` = два образи додатка. `otadata` відстежує, який слот
активний. Під час завантаження завантажувач читає `otadata` і
переходить до обраного слоту. Якщо запущений додаток обривається до
`esp_ota_mark_app_valid`, завантажувач повертається до іншого слоту
при наступному завантаженні.

## Процес завантаження

WebUI System → Firmware → Update АБО HTTP:

```
POST /api/ota
Content-Type: multipart/form-data
Content-Length: 1900000

<двійковий образ прошивки>
```

Що відбувається:

1. HTTP-обробник відкриває неактивний розділ (`esp_ota_begin`).
2. Передає фрагменти прямо з тіла запиту у flash, перевіряючи
   заголовок (магічне число + тип чипа).
3. На `EOF` завершує запис (`esp_ota_end`).
4. Позначає новий розділ як той, що очікує завантаження
   (`esp_ota_set_boot_partition`).
5. Повертає `{"ok":true, "next": "ota_1", "size": 1879040}`.
6. WebUI пропонує користувачу підтвердити перезавантаження.

Новий образ перебуває **в очікуванні** — ще не перевірений. Під час
перезавантаження:

1. Завантажувач бачить очікування і завантажується з нового слоту.
2. Додаток ініціалізується; `App::on_start` (після успішної
   ініціалізації менеджерів) викликає
   `esp_ota_mark_app_valid_cancel_rollback()`.
3. Якщо додаток досягнув цього виклику, новий образ стає **дійсним**;
   інакше при наступному перезавантаженні завантажувач не бачить
   маркера перевірки і автоматично повертається до попереднього слоту.

## Підтвердження та відкат

```
POST /api/ota/confirm   # явна позначка дійсності користувачем
POST /api/ota/rollback  # негайно завантажити ІНШИЙ розділ
```

`confirm` — це no-op, якщо додаток уже самостійно підтвердився
(типово). Корисно, якщо потрібен поетапний випуск: відправляйте з
прапором перевірки, що типово виставлений у false, і змушуйте
користувача натиснути "Confirm" у WebUI.

`rollback` міняє завантажувальний розділ і перезавантажує. Використовуйте,
коли нова прошивка запускається технічно успішно, але виявляє баги,
які самоперевірка не може виявити.

## Ключі стану

| Ключ | Примітки |
|---|---|
| `ota.active_partition` | `"ota_0"` або `"ota_1"`. |
| `ota.next_partition` | Куди підготовлено образ, що очікує. |
| `ota.app_version` | З `CONFIG_APP_PROJECT_VER` (Kconfig). |
| `ota.idf_version` | Версія ESP-IDF, вбудована в збірку. |
| `ota.last_update_unix` | Коли завершилося останнє успішне оновлення. |

## Довідник HTTP-ендпойнтів

| Метод + шлях | Тіло | Призначення |
|---|---|---|
| `GET /api/ota` | — | Повертає інформацію про активний/наступний розділ та версії. |
| `POST /api/ota` | binary | Потік прошивки. Повертає розмір та цільовий слот. |
| `POST /api/ota/confirm` | — | Позначити прошивку в очікуванні як дійсну (скасувати відкат). |
| `POST /api/ota/rollback` | — | Завантажити попередній розділ; негайне перезавантаження. |

Автентифікація: HTTP Basic, ті самі облікові дані адміністратора, що й
для решти API.

## Безпека

- HTTP Basic Auth — єдиний вбудований захист. **Не виставляйте порт 80
  в Інтернет**, не помістивши OTA за VPN, firewall або зворотним
  проксі з додатковою автентифікацією.
- Опціонально: увімкніть secure boot (`CONFIG_SECURE_BOOT`) і шифрування
  flash у Kconfig ESP-IDF. Це додає криптографічну цілісність на рівні
  завантажувача. Обов'язково у виробництві, де пристрій фізично
  доступний.
- Опціонально: підписані образи прошивки. Налаштовуються через опції
  Kconfig у секції `signing`. Завантажувач відхиляє образи без дійсного
  підпису.

## Пам'ять і продуктивність

- HTTP-сервер тримає буфер ~4 КБ для передачі фрагментів; прошивка не
  використовує додаткову купу.
- Швидкість запису у flash: ~150 КБ/с на типовому ESP32-S3 (обмежено
  часом стирання SPI-флеш, а не WiFi).
- Загальний час оновлення для прошивки ~1.8 МБ: ~12-15 секунд.

## Типові помилки

**Часткове завантаження → пошкодження:** HTTP-обробник відкидає
будь-яке незавершене завантаження; неактивний розділ залишається
недоторканим (перерваний цикл `esp_ota_begin/end` ніколи не позначає
новий слот як цільовий для завантаження). Повторіть завантаження.

**Втрата WiFi посеред оновлення:** якщо браузер користувача
від'єднується, HTTP-запит обривається з боку пристрою. Те саме, що й
часткове завантаження — чистий стан. Повторіть.

**Самоперевірка ніколи не спрацьовує:** якщо ваші модифікації ламаються
до хука перевірки (наприклад, assert у Phase 1 init), нова прошивка
завантажується, падає, і завантажувач відкочується при наступній
спробі. Скористайтеся послідовною консоллю, щоб побачити аварійний
вивід.

**Очікування завантаження у виробництві:** ніколи не розгортайте з
вимкненим автоматичним відкатом. Завжди дозволяйте принаймні 1 цикл
перезавантаження пройти, перш ніж оголошувати нову прошивку
"стабільною".

**Сумнівні мережі:** OTA через зайняту публічну WiFi може завершитися
таймаутом. Запускайте оновлення зі стабільного LAN-з'єднання.
