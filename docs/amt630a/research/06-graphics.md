# AMT630A — Графіка: бітмапи, іконки, бари, лого (дослідження 06)

> Дослідник: реверс/інтеграція AMT630A. Ціль: режим 4bpp-bitmap вікна (FB05 bit7),
> прозорість бітмапа (FB35), малювання іконок/барів/лого, завантаження довільної
> 4bpp-графіки у FONT RAM.
>
> **Джерела:** ENGELS.A22 (OEM-дизасемблер nocash, найбагатший), AMT630A.A22 (clean),
> user-спека `AMT630A_user_spec.md` розд. 4–7, Fizik `display_1306.h` / `logo.h` / `AMT630.h`.
> Адресація: банк `FBxx` (OSD) = I²C 7-біт **0x5B**; low-байт MCU-адреси = № регістра.

---

## 0. TL;DR (найважливіше)

1. **Графіка на AMT630A = тайли у FONT RAM + вікно у режимі bitmap.** Окремого
   «framebuffer» немає. Будь-яка графіка (іконка, бар, лого) — це набір 16×N-піксельних
   тайлів, завантажених у FONT RAM (коди `1C0h+`), розкладених у BGMAP вікна.
2. **Два формати тайлів:** **1bpp** (як ROM-шрифт, як завантажує OEM-прошивка — підтверджено
   асемблером) і **4bpp 16-кольоровий** (увімкнення через `FB05h.bit7`, палітра `FB36h..FB55h`).
   **4bpp — слабко доведений** (OEM-прошивка його НЕ використовує — функції позначені «unused»).
3. **Завантаження у FONT RAM по I²C — лише ручне** (`FB02h/0Fh` addr + `FB04h`/`FB03h` data).
   DMA (`osd_upload_font_characters_via_dma`) потребує `SFR C6h.bit3` — **CPU-only, недоступний по I²C** (підтверджено в ENGELS @9ED3h).
4. **Готові ROM-іконки** (бари батареї/сигналу) існують у вбудованому 418-символьному ROM
   (`137h+` за user-спекою) — але **точні коди в ENGELS НЕ верифіковані** (конфлікт, див. §6).
5. **Бар/прогрес-бар** простіше робити **текстовими тайлами** (8 рівнів заповнення як
   окремі символи), а не 4bpp-графікою — це шлях, найближчий до доведеного робочого коду.
6. **Fizik `logo.h` / `myBitmap`** — це **НЕ** AMT630A-графіка: gzip-JPEG для WiFi-вебсторінки
   + 1bpp-бітмап для **SSD1306** OLED (Adafruit_GFX). До AMT630A прямо непридатне, але
   формат 1bpp-бітмапа SSD1306 **конвертується** у тайли AMT630A (див. §8).

## 1. Архітектура графіки AMT630A (з ENGELS register map)

OSD-рушій тайловий. «Пікселів» напряму не пишемо — пишемо **тайли** (16×N px) у FONT RAM
і **номери тайлів** у BGMAP. Графіка = ті самі тайли, лише трактовані як 1bpp або 4bpp.

| Область | Розмір | Призначення |
|---------|--------|-------------|
| BGMAP RAM | 200h записів | «екран» вікна: № тайла (10-біт) + атрибут (FB10h) |
| FONT RAM | «4096×16 bits» (8 КБ) | завантажувані тайли (шрифт + графіка), коди `1C0h+` |
| FONT ROM | 418 символів | вбудовані: цифри/латиниця/частина кирилиці/символи |

ENGELS (рядок 3244–3248), дослівно:
```
;note: AMT630A said to have "Built-in 418-character font ROM"
;that would be "1A2h" characters (?)
;probably 1A0h chars at 0020h..001BFh, plus 2 extra chars?
;and custom user RAM chars at 01C0h and up.
;font RAM is said to be "4096x16 bytes" (or rather "bits"?)
```

**Висновок:** ROM-тайли = коди `020h..1BFh`; RAM-тайли (твоя графіка/кирилиця) = `1C0h+`.

## 2. Регістри графіки/бітмапа (банк FBxx / I²C 0x5B)

Витяг з блоку I/O-портів ENGELS (рядки 313–411), **дослівні коментарі nocash**:

| Рег (MCU) | I²C reg | Ім'я (ENGELS) | Призначення / нотатки |
|-----------|---------|---------------|-----------------------|
| `FB02h` | `0x02` | `IO_OSD_font_addr_lsb` | addr для ручного vram-upload (index*factor) |
| `FB0Fh` | `0x0F` | `IO_OSD_font_addr_msb` | bit4-7 = NOT R/W |
| `FB03h` | `0x03` | `IO_OSD_font_data_lsb` | data для ручного upload (запис тут латчить обидва) |
| `FB04h` | `0x04` | `IO_OSD_font_data_msb` | data msb |
| **`FB05h`** | `0x05` | `IO_OSD_window_enable_bits` | bit0-4=вікна 0-4; **bit6=hides windows (TEXT on/off)**; **bit7=BITMAP on/off** |
| `FB06h` | `0x06` | `IO_OSD_misc_transp_enable` | upper2bit=semitransp.ctrl |
| `FB0Ch` | `0x0C` | `IO_OSD_bright_transp_level` | upper3bit=brightness, lower3bit=transparency |
| `FB11h` | `0x11` | `IO_OSD_bitmap_start_lsb` | № першого BITMAP-символу (завжди `28h`); коди < цього = TEXT, ≥ = BITMAP |
| `FB70h` | `0x70` | `IO_OSD_bitmap_start_msb` | msb до FB11h; завжди `00h`; bit2-7 NOT R/W |
| **`FB35h`** | `0x35` | `IO_OSD_bitmap_transp_misc` | **bit4 = bitmap TRANSP color0**; bit3=SOMEpixX, bit5=1pixY; bit6-7 NOT R/W; fixed 00h в OEM |
| `FB36h..FB55h` | `0x36..0x55` | `IO_OSD_bitmap_colors` | **16 слів = палітра 4bpp** (32 байти). EVEN-адреси: bit4-7 NOT R/W |
| `FB76h` | `0x76` | `IO_OSD_char_xsiz` | ширина тайла px (lower5bit, max ~24) |
| `FB77h` | `0x77` | `IO_OSD_char_ysiz` | висота тайла px (lower6bit) |
| `FB78h` | `0x78` | `IO_OSD_xyflip` | bit4=TileXflip, bit5=MapXflip, bit6=TileYflip, bit7=MapYflip |

> **Важливо (конфлікт із розумінням):** `FB05h.bit7` НЕ є «4bpp-режим вікна» в чистому
> вигляді. Дослівний коментар nocash: **«bit7: bitmap, BITMAP ON/OFF»**, а bit6 —
> **«hides windows, TEXT ON/OFF»**. Тобто FB05h має два глобальні перемикачі шарів:
> TEXT-шар (bit6) і BITMAP-шар (bit7), плюс per-window enable bit0-4. Це **глобальний
> вибір трактування**, не прапор окремого вікна. Точна семантика «як вікно стає
> 4bpp» у дизасемблері НЕ розкрита — функції, що чіпають bit7 (@AA7Eh), позначені
> **«(unused?)»** і ніколи не викликаються OEM-прошивкою.

## 3. Формат тайла FONT RAM — ПІДТВЕРДЖЕНО (1bpp)

Найцінніший факт: у ENGELS є **повна таблиця даних `main_font`** (рядки 3239+) із
дослівними коментарями. Це доводить формат 1bpp-тайла поза сумнівом.

```
main_font:
        ;20h-byte blocks, aka 10h-word blocks, aka 16x16pix ?
        ;actual font size is 12x16pix (but 12pix is rounded up to 16bit per word)
        ;1540h bytes (5440 bytes, 2720 words) (AAh*20h=1540h)   ; = 0AAh=170 chars
0981 ... dw 00000h,01F00h,03F80h,071C0h,060C0h,060C0h,064C0h,064C0h ;01C1h "0"
0991 ... dw 064C0h,060C0h,060C0h,071C0h,03F80h,01F00h,00000h,00000h
```

**Розбір формату:**
- **1 тайл = 10h слів (16 слів) = 20h байт** для розміру 12×16 (12px ширини
  округлено до 16-бітного слова на ряд; 16 рядів = 16 слів).
- **1 слово = 1 ряд**, 16 біт = 16 пікселів. **MSB-вирівнювання зліва**: напр. символ "0"
  ряд 2 = `01F00h` = `0001 1111 0000 0000b` → пікселі 4-8 увімкнені (тіло цифри по центру
  12px-комірки). Старший біт слова (bit15) = крайній лівий піксель.
  > Зверни увагу на конфлікт із user-спекою §7, яка пише «bit0 = лівий піксель».
  > **Дизасемблер каже інакше: лівий піксель = старший біт (MSB-first).** Дані `main_font`
  > це доводять однозначно (тіло гліфів зміщене вліво-в-центр, а не в молодші біти).
  > **Звіряти на бенчі**, але довіряти дизасемблеру.
- **Розмір тайла залежить від FB76h/FB77h.** Алгоритм OEM (`osd_upload_font_characters_manually`
  @783Dh) обчислює «INNER.LEN» (слів на символ) так:
  - якщо `xsiz ≤ 16`: INNER.LEN = `ysiz` (1 слово на ряд);
  - якщо `xsiz > 16` (до 24): INNER.LEN = `ceil(ysiz*3/2)` (1.5 слова на ряд → 24px у 2 словах).

  Тобто для 12×16 → 16 слів; для 16×22 (кирилиця) → 22 слова; для 24×22 → 33 слова.

## 4. Завантаження тайла у FONT RAM по I²C — ПІДТВЕРДЖЕНО (ручний шлях)

ENGELS `osd_upload_font_characters_manually` (@782Bh) — еталонний алгоритм. Ключові кроки:

```asm
; INNER.LEN (слів на символ) = f(FB76h, FB77h)  ; @783D..787E
788A 90 FB 02   mov dptr,IO_OSD_font_addr_lsb     ; font_addr = INNER.LEN * dest_index
;  outer loop по символах, inner loop по словах:
78BD 90 FB 0F   mov dptr,IO_OSD_font_addr_msb     ; addr msb = (INNER.LEN*idx + word*idx ...) >> 8
78D9 90 FB 04   mov dptr,IO_OSD_font_data_msb     ; СПОЧАТКУ msb-байт слова
78EE 90 FB 03   mov dptr,IO_OSD_font_data_lsb     ; ПОТІМ lsb-байт (запис тут латчить ОБИДВА у VRAM)
```

**Практичний рецепт по I²C (dev=0x5B):**
```c
// Завантажити один тайл 16xH (1bpp) у FONT RAM код (1C0h + ram_index)
// word_addr = ram_index * words_per_tile   (words_per_tile = H для xsiz<=16)
void amt_load_tile(uint8_t ram_index, const uint16_t *rows, uint8_t H) {
    uint16_t base = (uint16_t)ram_index * H;        // адреса в словах
    for (uint8_t r = 0; r < H; r++) {
        uint16_t a = base + r;
        amt_w(0x5B, 0x0F, (a >> 8) & 0x0F);          // FB0Fh font_addr_msb (bit4-7 NOT R/W)
        amt_w(0x5B, 0x02, a & 0xFF);                 // FB02h font_addr_lsb
        amt_w(0x5B, 0x04, (rows[r] >> 8) & 0xFF);    // FB04h data_msb  ← СПОЧАТКУ
        amt_w(0x5B, 0x03, rows[r] & 0xFF);           // FB03h data_lsb  ← латчить обидва
    }
}
```

**Захист від glitch (з user-спеки §7, підтверджено логікою init):**
1. `amt_w(0x5B,0x05,0x00)` — вимкнути ВСІ вікна (FB05h=0) перед заливкою;
2. залити всі тайли;
3. `amt_w(0x5B,0x05, маска)` — увімкнути назад.
> DMA-варіант недоступний: @9ED3h `or [SFR_IO_memory_system],08h` (= `SFR C6h.bit3`)
> «pause FONT rendering during DMA upload» — це CPU-SFR, **по I²C недосяжний**. Тому
> єдиний захист — вимкнення вікон, не C6h.

## 5. Режим 4bpp-bitmap — теорія (СЛАБО доведено, OEM не вживає)

Усе нижче — реконструкція з register-map + UNUSED-функцій; OEM-прошивка працює **лише 1bpp**.

**Що відомо:**
- **Палітра 4bpp = `FB36h..FB55h`** (16 слів). ENGELS дослівно: *«sixteen words (20h bytes)
  (used only by an UNUSED function) maybe 16-color bitmap palette?»*. Функція
  `osd_set_bitmap_palette` (@A2A2h) пише пари байт у ці регістри — **але вона `(unused?)`**.
- **Прозорість 4bpp = `FB35h.bit4`** («bitmap TRANSP color0?»). Тобто index 0 у 4bpp-тайлі =
  прозорий (видно відео крізь), аналог color 0 у тексті.
- **Увімкнення шару = `FB05h.bit7`** (через UNUSED `@AA7Eh or a,80h`).
- **Старт-код bitmap-символів = `FB11h`** (=`28h` → перший bitmap-тайл має код `1C0h+28h=1E8h`).
  ENGELS init: `mov r7,28h ; call osd_set_bitmap_start` (@A383h). Коди `1C0h..1E7h` = TEXT-RAM,
  `1E8h+` = BITMAP-RAM. **Розділення TEXT/BITMAP у FONT RAM керується саме FB11h.**

**Формат 4bpp-тайла (гіпотеза, НЕ верифіковано):** ймовірно 4 біти/піксель, 16px ширини =
8 байт/ряд = 4 слова на ряд для 16px… але це **не підтверджено даними** (немає 4bpp-таблиці
в ROM). Той самий `osd_upload_font_characters_manually` для 4bpp **не пристосований** (він
рахує INNER.LEN з xsiz у пікселях як для 1bpp). **Висновок: 4bpp по I²C — дослідницький
ризик, перевіряти лише на бенчі покроково.**

**Палітра 4bpp (формат пар у FB36h+):** за аналогією з фіксованими кольорами 1-6
(`FB56h..FB61h`, формат 4:4:4 RGB — msb=Blue, lsb=Green/Red, з коментарів ENGELS
377-388: color1=`00h,0Fh`=red, color2=`00h,F0h`=green, color3=`0Fh,00h`=blue,
color4=`00h,FFh`=yellow, color5=`0Fh,F0h`=cyan, color6=`0Fh,FFh`=white).

## 6. ROM-іконки (бари батареї/сигналу) — КОНФЛІКТ ДЖЕРЕЛ

**User-спека §4** стверджує: `137h..13Bh` = «символи батареї», ROM має «бари батареї/сигналу».

**ENGELS (read-only перевірка):** прямих міток `battery_icon` / `signal_icon` у дизасемблері
**НЕ знайдено**; адреса `137h` як код символу в коді не зустрічається. Знайдено лише
`xxx_unused_tile_numbers` (@23F9h) — таблиці номерів `1C0h..024Fh` для **bitmap**
(«tilenumbers for bitmap? with 01C0h=blank»), але це RAM-діапазон, не ROM `137h`.

> **Невирішений конфлікт:** існування і коди ROM-іконок батареї/сигналу на `137h+` походять
> із user-спеки (зведення зовнішнього реверсу), **дизасемблером ENGELS не підтверджені**.
> Сам OEM-прилад малює статус **завантаженими тайлами** (extra_font_1/2, див. нижче), а не
> ROM-іконками `137h`. **Рекомендація:** не покладатися на ROM-іконки; малювати власні
> іконки/бари своїми тайлами у `1C0h+` (надійно, формат доведений §3-4).

**OEM реально завантажує додаткову графіку** (ENGELS init @A3A8h):
```asm
mov r2,extra_font_1/100h  ; 3AF4h (src in CODE)  ; 19h chars → vram index AAh..C2h
mov r2,extra_font_2/100h  ; 3EB4h               ; 07h chars → vram index C3h..C9h
call osd_upload_font_characters_manually
```
тобто 0x19+0x07 = 32 кастомні тайли (іконки/спецсимволи GUI) поверх 0xAA=170 основних —
**усе через ручний upload**, що ідеально лягає на наш I²C-шлях.

## 7. Fizik logo.h / display_1306.h — формат і придатність

**Що це насправді (read-only аналіз):**

| Файл/масив | Формат | Призначення | До AMT630A? |
|------------|--------|-------------|-------------|
| `logo.h: logo_jpg_gz[]` (3778 B) | gzip(`1f 8b 08`) + JPEG | **WiFi-вебсторінка** `/logo.jpg` (wifiupdate.h:61) | **Ні** (JPEG, не тайли) |
| `logo.h: favicon_ico_gz[]` (742 B) | gzip + PNG | favicon вебсторінки | Ні |
| `display_1306.h: myBitmap[]` (512 B) | **1bpp, 64×64** | лого на **SSD1306** OLED через `display.drawBitmap(32,0,myBitmap,64,64,1)` | **Опосередковано** (конвертовано — §8) |

**Бар-граф у Fizik (display_1306.h:287-298)** — RSSI-сканер: малює стовпчики крапок
`viewText(".", x, 45-i)` де `i = map(rssi,0,100,0,30)`. Це **SSD1306-специфічно** (Adafruit_GFX),
але **концепція прямо переноситься** на AMT630A: бар = N тайлів-стовпчиків з різним рівнем
заповнення (див. §9).

**`myBitmap` формат = MSB-first рядковий 1bpp**, 8 байт/ряд (64px), 64 ряди = 512 байт. Це
**той самий MSB-first**, що й тайли AMT630A (§3) → конвертація тривіальна (порізати на
16-піксельні стовпці × 16/22-рядкові тайли).

## 8. Рецепт: лого/довільна 1bpp-графіка на AMT630A

Лого 64×64 (як Fizik `myBitmap`) → розкласти на сітку тайлів і залити у FONT RAM.

1. **Обрати геометрію тайла** = розмір символу вікна (`FB76h`/`FB77h`). Напр. 16×16 →
   лого 64×64 = **4×4 = 16 тайлів**.
2. **Конвертувати** `myBitmap` (8 байт/ряд, MSB-first) → 16 тайлів по 16 слів. Для тайла
   (tx,ty): рядок r тайла = біти `[tx*16 .. tx*16+15]` рядка `ty*16+r` оригіналу, спаковані
   MSB-first у `uint16_t`.
3. **Залити** через `amt_load_tile()` (§4) у коди `1C0h + idx` (idx=0..15), вимкнувши вікна.
4. **Розкласти** 4×4 тайли у BGMAP вікна (osd_print аналог): для кожного ряду тайлів виставити
   addr і записати 4 коди `1C0h+ty*4+tx`.
5. **Атрибут** (`FB10h`): text-color 1-6 (з палітри `FB56h+`), bg=0 (прозорий) → лого
   поверх відео.

> Це **1bpp одноколірне** лого (силует). Для багатобарвного лого потрібен 4bpp (§5, ризик).
> Для статусних екранів силует достатній.

## 9. Рецепт: прогрес-бар / бар рівня (НАДІЙНИЙ, 1bpp-тайлами)

Найпрактичніший і доведений підхід — **8 тайлів-рівнів заповнення** (як «██▉▊▋▌▍▎▏»):

1. Згенерувати 8 (або 16) тайлів 16×H, де тайл k заповнений на `k/8` ширини (стовпці зліва).
   Кожен ряд = слово з k*2 старшими бітами = 1 (бо MSB=лівий).
   Напр. рівень 4/8 (12px-комірка): ряд = `0xFC00` (6 старших біт = піксели 1-6).
2. Залити їх у FONT RAM коди `1C0h..1C7h` (один раз при старті).
3. Бар довжини L символів для значення `v∈[0..1]`: заповнені комірки = `floor(v*L)` повних
   тайлів (код «full»), одна часткова комірка (код `1C0h+часткова_частина`), решта — порожній.
4. Записати ці коди у BGMAP рядок вікна (osd_print). Колір через `FB10h` атрибут.

**Перевага над 4bpp:** використовує лише доведений 1bpp-механізм; оновлення — лише запис
кодів у BGMAP (атомарно, без glitch); не потрібна сумнівна 4bpp-палітра.

**Іконка батареї:** 5 тайлів (рівні 0/25/50/75/100%) або 1 контурний тайл + динамічний
fill-тайл усередині. Малюється тим самим механізмом. **НЕ покладатися на ROM `137h`** (§6).

---

## 10. Рецепт: проста іконка (статичний символ)

1. Намалювати іконку як 1bpp-тайл 16×16 (або 16×22) MSB-first (тулза: PNG→тайл, той самий
   формат що `gen_osd_font.py` для кирилиці, лише без TTF — растер вручну).
2. `amt_load_tile(idx, rows, 16)` → код `1C0h+idx`.
3. Вивести у потрібну BGMAP-комірку з атрибутом кольору.

Для ModESP: розширити `tools/gen_osd_font.py` — додати режим «icon» (приймає PNG/растр,
видає той самий `.h`-масив 16-біт слів MSB-first, що й гліфи). Інтеграція в існуючий
`at7456e_renderer` потребує лише підміни «вивід-тайл» на I²C-запис у FONT RAM AMT630A.

## 11. Порядок дій для графіки (Шлях A, I²C 0x5B)

```
1. FB05h = 0x00                 ; вимкнути вікна (захист від glitch)
2. FB76h = ширина, FB77h = висота тайла (напр. 16,16 або 16,22)
3. (раз) залити тайли графіки/барів/лого у FONT RAM 1C0h+  (ручний upload §4)
4. (раз) палітра кольорів FB56h..FB61h (1bpp атрибути)  [4bpp: FB36h.. — ризик §5]
5. налаштувати вікно (розмір/позиція FB07/08/09/0A/0B)
6. розкласти коди тайлів у BGMAP вікна (FB00/0D addr + FB01 data + FB10 attr)
7. FB05h = маска вікон           ; увімкнути назад
8. цикл: оновлювати BGMAP-коди (бари/іконки) при зміні даних — атомарно
```

## 13. Практичний висновок під ModESP

- **Надійний шлях графіки = 1bpp-тайли у FONT RAM + BGMAP.** Доведено дизасемблером і
  механічно ідентичний завантаженню кирилиці (§4). Бари/іконки/лого — усе цим механізмом.
- **Прогрес-бар** — 8 тайлів-рівнів заповнення (§9), оновлення = запис кодів у BGMAP.
  Це рекомендований патерн (без 4bpp-ризику).
- **4bpp 16-кольорова графіка** — лишити на «дослідницький бенч»: регістри відомі
  (`FB05h.bit7`, `FB35h.bit4`, палітра `FB36h+`), але OEM її не вживає і формат тайла не
  верифікований. Спершу довести 1bpp, потім (за потреби кольору) обережно пробувати 4bpp.
- **ROM-іконки `137h`** — НЕ використовувати без бенч-верифікації (конфлікт §6); малювати свої.
- **Тулінг:** розширити `tools/gen_osd_font.py` режимом «icon/bitmap» (PNG/растр → 16-біт
  MSB-first слова), перевикористати завантажувач FONT RAM з кириличного шляху.

**Джерела:** ENGELS.A22 (@318-411 register map, @782B manual upload, @9EB7 DMA, @3239 main_font
data, @23F9 unused tile numbers, @A36C init_OSD_hardware, @A2A2/@AA73 unused 4bpp/flip);
AMT630A.A22 (clean, узгоджено); user-спека §4-7; Fizik display_1306.h/logo.h/AMT630.h.
