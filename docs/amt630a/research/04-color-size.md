# AMT630A — Колір, палітра, прозорість і розміри тексту (OSD)

> Дослідницький звіт. Ціль: РІЗНІ РОЗМІРИ тексту, колір/палітра, прозорість, яскравість/контраст/насиченість.
> Банк OSD `FBxx` → **I²C 7-біт `0x5B`** (запис: `0x5B`, reg=низький байт, value).
> Джерела: user-спека (`AMT630A_user_spec.md` розд. 4/6/10), ENGELS.A22 (OEM реверс, абсолютні адреси + імена IO_*),
> AMT630A.A22 (чиста прошивка-експериментаторка Korth), Fizik `AMT630.h` (доведений I²C).
> Усі hex-факти нижче перепровірені проти **виконавчого коду** прошивки, не лише проти таблиці регістрів.

---

## 0. Найважливіше (TL;DR для драйвера)

1. **Палітра 6 кольорів — ПРОГРАМОВАНА, не фіксована.** Реверс ENGELS показав живу функцію
   `osd_init_six_colors` (адреса `ABE8h`), яка під час старту **пише** значення у `FB56h..FB61h`.
   Коментар «fixed» у мапі регістрів стосується лише того, що OEM ставить дефолт і не змінює — але запис працює.
2. **Формат кольору — RGB444 у двох байтах:** `lsb = (G<<4)|R`, `msb = B` (нижні 4 біти). Реально 0..0Fh
   (спека каже «0..10, далі max» — це поведінка АЦП-рампи, не обмеження формату).
3. **Атрибут `FB10h`:** bit0-2 = колір тексту (FG), bit4-6 = колір фону (BG); 0=прозорий(відео), 1-6=палітра, 7=чорний.
4. **Різний розмір тексту — ДВА механізми:** (а) глобально `FB76h/FB77h` (xsiz/ysiz у пікселях) — на ВЕСЬ OSD;
   (б) **per-window scale** `FB32h` (вікно 0) та `FB33h/FB34h` (вікна 1-4) — ×1..×4 на кожне вікно окремо.
   Для «великого» і «дрібного» тексту одночасно → **різні вікна з різним scale**.
5. **Напівпрозорість:** `FB06h` bit6=master(фон), bit7=текст; `FB0Ch` bit0-2=рівень. Дефолт `FB0Ch=80h`
   (яскравість=4, прозорість=0). Підтверджено кодом `osd_set_semi_transparency` (`B18Bh`).
6. **OEM реально використовує char size 12×16px** (не 16×22 як у Fizik!) — `init_OSD_hardware` (`A36Ch`).
7. **Конфлікт із Fizik:** Fizik пише атрибут `0x09` і char size 16×22. OEM пише атрибут через FG/BG-байт і 12×16.
   Обидва робочі — деталі в розд. 7.

## 1. Палітра 6 кольорів — FB56h..FB61h (банк OSD, I²C 0x5B)

### 1.1 Карта регістрів і дефолтні значення

З ENGELS.A22 (рядки 376-389), значення в коментарях = те, що пише `osd_init_six_colors`:

| Колір | reg msb | reg lsb | Дефолт (msb,lsb) | RGB444 (R,G,B) | Сприйняття |
|-------|---------|---------|------------------|----------------|-----------|
| 0     | —       | —       | (фіксований)     | —              | **прозорий** (видно відео/синій BG) |
| 1     | `FB56h` | `FB57h` | `00h, 0Fh`       | R=15,G=0,B=0   | червоний  |
| 2     | `FB58h` | `FB59h` | `00h, F0h`       | R=0,G=15,B=0   | зелений   |
| 3     | `FB5Ah` | `FB5Bh` | `0Fh, 00h`       | R=0,G=0,B=15   | синій     |
| 4     | `FB5Ch` | `FB5Dh` | `00h, FFh`       | R=15,G=15,B=0  | жовтий    |
| 5     | `FB5Eh` | `FB5Fh` | `0Fh, F0h`       | R=0,G=15,B=15  | блакитний (cyan) |
| 6     | `FB60h` | `FB61h` | `0Fh, FFh`       | R=15,G=15,B=15 | білий     |
| 7     | —       | —       | (фіксований)     | —              | **чорний** |

### 1.2 ДОКАЗ що палітра програмована (ENGELS `ABE8h`)

```asm
osd_init_six_colors:
ABE8 90 FB 57    mov  dptr,IO_OSD_color_1_lsb
ABEB 74 0F       mov  a,0Fh
ABED F0          movx [dptr],a            ; color1 lsb = 0Fh  → R=15,G=0
ABEE 90 FB 56    mov  dptr,IO_OSD_color_1_msb
ABF1 E4          clr  a
ABF2 F0          movx [dptr],a            ; color1 msb = 00h  → B=0   ⇒ ЧЕРВОНИЙ
...                                       ; (аналогічно color2..6)
AC1F 90 FB 61    mov  dptr,IO_OSD_color_6_lsb
AC22 74 FF       mov  a,0FFh              ; color6 lsb = FFh  → R=15,G=15
AC25 90 FB 60    mov  dptr,IO_OSD_color_6_msb
AC28 74 0F       mov  a,0Fh               ; color6 msb = 0Fh  → B=15  ⇒ БІЛИЙ
AC2B 22          ret
```

Викликається з `init_OSD_hardware` (`A372h`). **Висновок:** будь-який з 6 кольорів можна перевизначити
по I²C записом у `FB56h..FB61h` — це звичайні R/W XRAM-порти.

### 1.3 Формат RGB444 — точне розкладання бітів

```
lsb-байт (напр. FB57h):  bit0-3 = Red(0..0Fh),  bit4-7 = Green(0..0Fh)
msb-байт (напр. FB56h):  bit0-3 = Blue(0..0Fh), bit4-7 = 0 (NOT R/W у деяких — пиши 0)
```
Перевірка на дефолтах: жовтий = R+G = lsb `FFh` (R=F,G=F), msb `00h` (B=0) ✔.
cyan = G+B = lsb `F0h` (G=F,R=0), msb `0Fh` (B=F) ✔.

> **Хелпер для драйвера:**
> ```c
> // r,g,b у 0..15
> void amt_set_color(uint8_t idx /*1..6*/, uint8_t r, uint8_t g, uint8_t b){
>     uint8_t msb_reg = 0x56 + (idx-1)*2;   // FB56,FB58,...
>     uint8_t lsb_reg = msb_reg + 1;        // FB57,FB59,...
>     amt_w(0x5B, lsb_reg, ((g & 0x0F)<<4) | (r & 0x0F));
>     amt_w(0x5B, msb_reg,  (b & 0x0F));
> }
> ```

### 1.4 16-кольорова bitmap-палітра (FB36h..FB55h) — бонус

ENGELS рядок 375: `FB36h..FB55h IO_OSD_bitmap_colors: defs 32` — шістнадцять RGB444-слів для 4bpp-графіки
(«used only by an UNUSED function»). Чиста прошивка (AMT630A.A22 `set_palette`, `10914h`) демонструє запис цієї
палітри з лінійною інтенсивністю (25/50/75/100%) — той самий формат RGB444 (B, G, R по 4 біти).
Для текстового OSD не потрібно; знадобиться лише якщо вмикати 4bpp-режим (`FB05h.bit7`).

## 2. Атрибут кольору символу — FB10h (FG/BG)

ENGELS рядок 332: `FB10h IO_OSD_bgmap_data_attr ;bit7:NOT R/W`.

| Біти   | Поле | Значення |
|--------|------|----------|
| bit0-2 | **FG** (колір тексту) | 0=прозорий, 1-6=палітра, 7=чорний |
| bit3   | (?) | не задокументовано; OEM не використовує |
| bit4-6 | **BG** (колір фону) | 0=прозорий(відео), 1-6=палітра, 7=чорний |
| bit7   | NOT R/W | пиши 0 |

`attr = (FG & 7) | ((BG & 7) << 4)`.

**Як прошивка виводить атрибут** (ENGELS `920Fh`, головний BGMAP-рендер):
```asm
920F 90 FB 10    mov  dptr,IO_OSD_bgmap_data_attr
9212 E5 0C       mov  a,[iram_tmp_window_attr]   ; на вікно зберігається один attr
9214 F0          movx [dptr],a                  ; ⇒ колір ставиться ПО-ВІКОННО, не по-символьно
```
Тобто OEM тримає **один колір на вікно**. Для різнокольорового тексту в одному вікні треба міняти
`FB10h` між групами символів (як це й робить Fizik — пише `FB10h` після кожного символу).

> **Важливо:** `FB10h` діє на наступні записи `data_lsb` (`FB01h`). Послідовність: спершу `FB10h` (attr),
> потім символи. Fizik пише attr ПІСЛЯ символу (рядок 201 `AMT630.h`) — працює, бо attr латчиться в ту ж
> BGMAP-комірку; але безпечніше виставляти attr ПЕРЕД групою символів.

## 3. РІЗНІ РОЗМІРИ ТЕКСТУ — головна вимога

Є **три рівні** керування розміром. Розрізняй їх:

### 3.1 Глобальний розмір комірки символу — FB76h / FB77h

| reg | поле | діапазон |
|-----|------|----------|
| `FB76h` | char X size у пікселях | bit0-4 (1..24px); bit5-7 NOT R/W |
| `FB77h` | char Y size у пікселях | bit0-5 (1..32px); bit6-7 NOT R/W |

Це **геометрія тайла шрифту** — скільки пікселів займає 1 символ і скільки 16-біт слів зчитується з FONT RAM.
ENGELS `osd_set_character_xysiz` (`BEB4h`):
```asm
osd_set_character_xysiz:   ;in: r5=ysiz, r7=xsiz
BEB4 90 FB 76    mov  dptr,IO_OSD_char_xsiz   // movx [dptr],r7   ; X
BEB9 A3          inc  dptr ;=IO_OSD_char_ysiz // movx [dptr],r5   ; Y
```
**OEM реально викликає це з 12×16px** (ENGELS `init_OSD_hardware`, `A375h`):
```asm
A375 7D 10       mov  r5,10h   ;ysiz = 16px
A377 7F 0C       mov  r7,0Ch   ;xsiz = 12px
A379 12 BE B4    call osd_set_character_xysiz   ; ⇒ комірка 12×16
```
> Зміна `FB76h/FB77h` змінює розмір **усього** OSD (бо це формат тайла) — НЕ годиться для «великий+дрібний одночасно».
> Це механізм «який у мене базовий шрифт», а не «це слово більше».

**Експериментальні нотатки Korth** (AMT630A.A22, `6868h`-`6873h`) — критичні граблі:
```
char_xsiz=16  → ок
char_xsiz=12  → ок (OEM default по X)
char_xsiz=24  → ок (max)
char_xsiz=1   → малює ЛИШЕ 1 піксель вертикально на 16-біт запис
char_xsiz=4   → малює 4-піксельний ряд
char_xsiz=8   → "goes crap diagonally": CHAR 0 перекриває CHAR 1
                 → фікс: використовувати лише CHAR 0 і CHAR 2 (через один)
```
Тобто за малих xsiz сусідні символи накладаються — для дрібного шрифту тримай xsiz ≥ 12, а дрібність роби scale-down або вузьким шрифтом.
Також `char_ysiz=24` дає той самий діагональний glitch (рядок 6875).

### 3.2 Per-window МАСШТАБ — FB32h (вікно 0), FB33h/FB34h (вікна 1-4) ← ОСНОВНИЙ механізм різних розмірів

Це **апаратне розтягування вже намальованого вікна** ×2/×3/×4 — НЕ змінює формат шрифту.
Дозволяє різний розмір **на кожне вікно одночасно** → саме те, що треба для «велике сповіщення» + «дрібний статус».

**Карта (ENGELS 371-373):**
| reg | вікна | формат |
|-----|-------|--------|
| `FB32h` | вікно 0 | bit0-3 = scale; bit4-7 NOT R/W |
| `FB33h` | вікна 1 і 2 | low nibble = вікно1, high nibble = вікно2; у кожному 2×2-біт (ScaleX bit0-1, ScaleY bit2-3) |
| `FB34h` | вікна 3 і 4 | low nibble = вікно3, high nibble = вікно4 |

**ДОКАЗ scale-функції** — ENGELS `osd_set_text_scale_r7` (`8E0Ch`), коментар автора:
```asm
osd_set_text_scale_r7:  ;in: r7=txt.scale (1..4) (1=normal, 2=double, 3=?, 4=?)
                        ;note: double size is used for NoSignal
```
Для **вікна 0** scale ≥2 додатково заповнює per-line bitmap-маски FFh у `FB2Bh..FB2Dh` (vscale) і
`FB2Fh..FB31h` (hscale) — це «розмазування» кожного рядка/пікселя для масштабів до 24px-символів, плюс
ставить старші біти `FB32h`:
```asm
8E2B 1F          dec r7            ; param-1
8E2C 1F          dec r7            ; param-2
8E2E C4          swap a            ;\ param*10h
8E32 25 E0       add a,a           ; param*40h+param*10h  → у FB32h
8E36 42 07       or  r7,a          ;
8E38 A3          inc dptr ;=FB32h  // and a,0Fh // or a,r7 // movx
```

**Демо різних масштабів** (AMT630A.A22, `8588h`-`8597h`) — прямий доказ, що FB32 циклює 0..3:
```asm
8588 ... IO_OSD_window_0_scale // mov a,00h   ;×1
8590 ... IO_OSD_window_0_scale // mov a,01h   ;×2
8592 ... IO_OSD_window_0_scale // mov a,02h   ;×3
8594 ... IO_OSD_window_0_scale // mov a,03h   ;×4
```
І для вікон 1-4 (AMT630A.A22 `8568h`,`8581h`):
```asm
8568 ... window_1_and_2_scale // mov a,10h    ; вікно2=scale1(high nib), вікно1=0
8581 ... window_1_and_2_scale // mov a,040h   ; вікно2 ScaleY-біт
8569 ... window_3_and_4_scale // mov a,32h
8582 ... window_3_and_4_scale // mov a,0c8h   ; різні X/Y масштаби на вікна 3 і 4
```

**Декодування FB33h/FB34h** (з коду `8E59h`-`8EC2h`, по 2-бітні поля):
- Низький напівбайт = перше вікно пари: `bit0-1 = ScaleX-1`, `bit2-3 = ScaleY-1` (0→×1, 1→×2, 2→×3, 3→×4).
- Високий напівбайт = друге вікно пари (ScaleX у bit4-5, ScaleY у bit6-7).
- Напр. `FB33h = 0x40` ⇒ вікно2: ScaleX=0(×1), ScaleY=1(×2) → текст подвоєний по вертикалі.
- `FB33h = 0x05` ⇒ вікно1: ScaleX=1(×2), ScaleY=1(×2) → ×2 в обидва боки.

> **БАГ OEM (ENGELS `8E87h`, `8EBC h`):** при оновленні масштабу вікон 2 і 4 код робить `and a,0F0h`
> замість `0Fh` — тобто **затирає сусіднє вікно (1/3) у тій самій парі**. Коментар Korth прямо: `;<-- BUG`.
> Наслідок для нас: якщо керуєш scale **по I²C напряму** (а не через цю прошивкову функцію) — пиши весь байт
> `FB33h`/`FB34h` сам, тримаючи тіньову копію обох напівбайтів. Так баг обходиться.

### 3.3 РЕКОМЕНДАЦІЯ під «великий+дрібний одночасно»

| Сценарій | Як зробити |
|----------|-----------|
| Базовий шрифт середній | один раз `FB76h=12, FB77h=16` (як OEM) або `16/22` (як Fizik) |
| Дрібний статус | окреме вікно (напр. вікно 0) зі scale ×1 (`FB32h=0`) |
| Велике сповіщення | окреме вікно (напр. вікно 1) зі scale ×2/×3 через `FB33h` low-nibble |
| Усе разом | різні вікна, кожне зі своїм scale; вікна вмикаються бітами `FB05h.bit0-4` |

> Тобто **різний розмір тексту = різні OSD-вікна з різним per-window scale**. FB76/77 — глобальна база;
> FB32/33/34 — індивідуальний множник. Комбінація дає ×1..×4 на кожне вікно.

## 4. Напівпрозорість (відео крізь OSD) — FB06h / FB0Ch

ENGELS рядки 319, 328:
- `FB06h IO_OSD_misc_transp_enable` — upper2bit = semitrans.ctrl.
- `FB0Ch IO_OSD_bright_transp_level` — upper3bit=яскравість OSD, **lower3bit=прозорість**, middle2bit=?.

**ДОКАЗ механізму** — ENGELS `osd_set_semi_transparency` (`B18Bh`):
```asm
B190 90 FB 06   mov dptr,IO_OSD_misc_transp_enable
B194 44 40      or  a,40h    ;bit6=1  → master enable (напівпрозорий ФОН)
...
B19B 44 80      or  a,80h    ;bit7=1  → також напівпрозорий ТЕКСТ (опційно)
B1A4 54 7F      and a,7Fh    ;bit7=0  → текст НЕ напівпрозорий
...
B1A7 90 FB 0C   mov dptr,IO_OSD_bright_transp_level
B1AB 54 F8      and a,0F8h   ;\ очистити bit0-2
B1AD 4B         or  a,r3     ;/ виставити рівень (0..7)
```
Коментар у коді: рівень `0 = invisible .. 7 = near solid`.

| reg | біт | дія |
|-----|-----|-----|
| `FB06h` | bit6 | master enable напівпрозорості (фон) |
| `FB06h` | bit7 | додатково напівпрозорий текст |
| `FB0Ch` | bit0-2 | рівень прозорості 0(невидимо)..7(майже непрозоро) |
| `FB0Ch` | bit5-7 | яскравість OSD (0..7), дефолт 4 (`80h`) |

**Дефолт** (AMT630A.A22 init-table рядок 3895-3896): `FB06h=00h` (прозорість вимк.), `FB0Ch=80h`
(яскравість=4=norm, прозорість=0).

> **Граблі прозорості** (AMT630A.A22 `6036h`-`6038h`): нетипові значення `FB0Ch` (`08h/10h/18h`) →
> «flimmers all colors» (мерехтіння всіх кольорів, особливо в DIAG-меню та RGB-grayscale). Тримайся
> bit0-2 у межах 0..7 і не чіпай middle-біти.

### Рецепт «статус поверх живого відео»
```c
amt_w(0x5B, 0x06, 0x40);   // FB06: master semi-transp ON (фон)
amt_w(0x5B, 0x0C, (4<<5) | 0x05);  // яскравість 4, рівень прозорості 5  = 0x85
// текст лишається непрозорим (FB06.bit7=0) → читабельний поверх відео
```

## 5. Яскравість / контраст / насиченість / tint — банк FFxx (I²C 0x5A)

ENGELS рядки 926-929 (та таблиця калібрування 11373-11381):

| reg | параметр | Дефолт NTSC/RGB-вар. | Дефолт «інша» гілка |
|-----|----------|----------------------|---------------------|
| `FFD3h` | контраст    | `7Eh` | `80h` |
| `FFD4h` | яскравість  | `8Eh` | `80h` |
| `FFD5h` | tint (NTSC) | `00h` | `00h` |
| `FFD6h` | насиченість | `38h` | `30h`/`36h` |

> Спека («Medium» = `7E/8E/38/00`) збігається з гілкою `lcd_rgb_variant=1`. ✔

**Запис у коді** (ENGELS `7646h`+): значення проганяються через `xlat_bright_contrast_saturation_to_hex_values`
(min/max/medium з NVS) перед записом у `FFD3/D4/D6`. Для I²C-керування можна писати hex напряму
(`amt_w(0x5A, 0xD4, value)`), пропускаючи xlat.

**Tint-шкала** (ENGELS `xlat_tint_to_hex_values` `A7A4h`):
- 0..100% мапиться так, що **50% → `00h`**; 0% → `94h` (bit7=1), 49% → `80h`; 51% → `00h`, 100% → `62h` (bit7=0).
- Тобто `FFD5h.bit7` = знак відхилення відтінку. Дефолт `00h` = нейтральний.

### БАГ tint (FFD5h.bit7) — підтверджено
Спека: встановлення `FFD5h.bit7` ламає декодування кольору PAL, хоча tint має діяти лише на NTSC.
ENGELS `B181h` (`@@is_60hz_assume_ntsc`) показує, що tint-меню вмикається лише для NTSC/PAL60
(`or a,02h`). Реверс Korth прямо позначає, що bit7 псує PAL-колір.
**Правило: НЕ виставляй `FFD5h.bit7`.** Тримай tint у діапазоні, де bit7=0 (тобто ≥51% за шкалою xlat, або просто `00h`).

## 6. ГОТОВІ РЕЦЕПТИ

### 6.1 «Сповіщення великим червоним» (окреме вікно, ×2, червоний)
```c
// Налаштування вікна 1 (приклад) великим масштабом
amt_w(0x5B, 0x12, len);          // FB12: window1 size_x (символів)
amt_w(0x5B, 0x13, 0x01);         // FB13: window1 size_y = 1 рядок
amt_w(0x5B, 0x33, 0x05);         // FB33: вікно1 ScaleX=2,ScaleY=2 (×2×2)  (low nibble=0b0101)
amt_w(0x5B, 0x05, 0x03);         // FB05: вікна 0 і 1 ON
// колір 1 = червоний (дефолт уже червоний, але для певності):
amt_set_color(1, 15, 0, 0);
// атрибут: FG=color1(червоний), BG=прозорий
amt_w(0x5B, 0x10, (1 & 7) | (0 << 4));   // = 0x01
osd_print_to_window1("УВАГА");
```

### 6.2 «Дрібний статус сірим» (вікно 0, ×1, сірий)
```c
amt_w(0x5B, 0x32, 0x00);         // FB32: вікно0 scale ×1
// «сірий» = напівяскравий білий: R=G=B≈8
amt_set_color(6, 8, 8, 8);       // перевизначаємо color6 у сірий (або беремо вільний color)
amt_w(0x5B, 0x10, (6 & 7) | (0 << 4));   // FG=color6(сірий), BG=прозорий  = 0x06
osd_print_to_window0("5800 A DET -72 BAT85");
```

### 6.3 «Зелений OK на чорному тлі»
```c
// зелений уже color2; чорний фон = BG=7
amt_w(0x5B, 0x10, (2 & 7) | (7 << 4));   // FG=2(зелений), BG=7(чорний) = 0x72
```

### 6.4 «Жовтий поверх живого відео (напівпрозорий фон)»
```c
amt_w(0x5B, 0x06, 0x40);                 // FB06 master semi-transp (фон)
amt_w(0x5B, 0x0C, (4<<5) | 5);           // яскравість4, рівень5 = 0x85
amt_w(0x5B, 0x10, (4 & 7) | (0 << 4));   // FG=color4(жовтий), BG=прозорий = 0x04
```

### Найважливіша невирішена розбіжність (#5 — атрибут Fizik 0x09)
Fizik `osdPrint` пише `writeCommand(0x5B,0x10,0x09)` і коментує «FG=білий, BG=прозорий».
Але за картою регістрів `0x09 = 0b0000_1001`: FG(bit0-2)=`001`=**color1 (червоний за дефолтом)**, bit3=1.
Можливі пояснення: (а) на платі Fizik палітра перевизначена і color1=білий; (б) bit3 має значення
(можливо «яскравий» прапор). **Безпечніший шлях для ModESP:** не копіювати магічне `0x09`, а
явно `attr = (FG&7)|((BG&7)<<4)` (bit3 не чіпати) і керувати кольором через перевизначення палітри FB56-61.

| reg (I²C 0x5B) | назва | призначення |
|----------------|-------|-------------|

## 9. Дії «перевірити на бенчі»
1. **Атрибут `0x09` Fizik** — який реальний колір дає (#5). Звірити color1 на конкретній платі.
2. **Per-window scale FB33/FB34** — переконатися, що прямий I²C-запис повного байта дає очікувані ×2/×3
   на вікнах 1-4 (обхід OEM-багу `and 0F0h`).
3. **char_xsiz<12** — підтвердити «overlap» glitch; визначити мінімальний безпечний дрібний розмір.
4. **FB0Ch level** — підібрати рівень напівпрозорості без «flimmer» (Korth бачив мерехтіння за 08/10/18h —
   але це інші біти; перевірити чисті 0..7 у bit0-2).
5. **Палітра по I²C** — підтвердити, що запис у FB56-61 ззовні (не з MCU) реально змінює колір.
