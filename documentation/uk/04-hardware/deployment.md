# Deployment — flash, monitor, factory reset

> 📖 **In English:** [documentation/en/04-hardware/deployment.md](../../en/04-hardware/deployment.md)

Ця сторінка покриває робочий процес для розміщення прошивки **на**
фізичному пристрої ESP32, робочий процес із живою консоллю та як
відновитися з пошкодженої конфігурації. Для оновлень через ефір вже
розгорнутих пристроїв див. **[ota.md](ota.md)**.

ВИМАГАЄ: інструментарій ESP-IDF v5.x. Див.
**[../01-getting-started/installation.md](../01-getting-started/installation.md)**.

## Build → flash → monitor

```
idf.py build
idf.py -p COM4 flash
idf.py -p COM4 monitor
```

(`COM4` на Windows; `/dev/ttyUSB0` на Linux; `/dev/cu.usbserial-*`
на macOS.)

`flash` записує три ділянки:

1. **Завантажувач** (`build/bootloader/bootloader.bin`).
2. **Таблиця розділів** (`build/partition_table/partition-table.bin`).
3. **Додаток** (`build/<project>.bin`) — у `ota_0`.

Розділ даних LittleFS (`build/data/*.bin`) потребує окремого кроку:

```
idf.py build flash_data
```

або як частина повного розгортання:

```
idf.py build flash flash_data monitor
```

`flash_data` — це кастомна ціль CMake (див. `CMakeLists.txt` у корені
проєкту), яка збирає образ LittleFS із теки `data/` і записує його у
розділ `littlefs`.

## Що у розділі даних

```
data/
├── www/               # статичний бандл WebUI (HTML/JS/CSS)
├── scenarios/         # скомпільовані рецепти *.modr
├── i18n/              # пакети перекладів
└── (інші статичні ресурси)
```

`generate_ui.py` і `compile_scenario.py` наповнюють частину цього у
теці складання; решта зберігається у git.

## Monitor — жива послідовна консоль

```
idf.py monitor
```

Показує все, що логується через `ESP_LOGI`/`ESP_LOGW` тощо,
кольорово закодоване за рівнем журналу. Ctrl-] для виходу.

Корисні гарячі клавіші всередині монітора:

- `Ctrl-T Ctrl-X` — вийти і скинути пристрій.
- `Ctrl-T Ctrl-F` — декодувати backtrace наступної паніки.
- `Ctrl-T Ctrl-Y` — переключити фільтри виводу (наприклад, приховати
  info-рівень).

Для тривалих розгортань скористайтеся `picocom` і логуйте у файл:

```
picocom -b 115200 /dev/ttyUSB0 | tee modesp.log
```

## Factory reset

Два шляхи.

**З WebUI:** System → Factory reset → confirm. Виконує:

```
POST /api/factory-reset
```

Що це робить:

1. Стирає розділ `nvs` (`nvs_flash_erase()`).
2. Перезавантажує.

Після перезавантаження весь збережений стан повертається до типових
значень (немає облікових даних WiFi, немає збереженої конфігурації,
типова автентифікація). Пристрій переходить у запасний режим AP, бо
`wifi.ssid` порожній.

**З командного рядка:**

```
idf.py -p COM4 erase-flash
idf.py -p COM4 flash flash_data
```

`erase-flash` стирає УСЕ (завантажувач, таблицю розділів, додаток, NVS,
LittleFS). Використовуйте лише коли потрібен гарантовано чистий
пристрій — наприклад, при зміні розмітки розділів.

## Типові робочі процеси

### Перша прошивка свіжого пристрою

```
idf.py build
idf.py -p COM4 erase-flash
idf.py -p COM4 flash flash_data monitor
```

Після налаштування WiFi у запасному режимі AP або через початкові
облікові дані пристрій доступний у локальній мережі за адресою
`modesp-<id>.local`.

### Оновлення лише розділу даних (наприклад, нового бандла WebUI)

```
idf.py build flash_data
```

Додаток продовжує працювати без змін. Нові дані доступні негайно
(LittleFS монтується при завантаженні).

### Оновлення лише прошивки

```
idf.py build flash monitor
```

Пропускає розділ даних. Додаток перезавантажується з новою прошивкою;
дані зберігаються.

### Цикл smoke-тестування

```
idf.py build && idf.py -p COM4 flash flash_data monitor
```

Один рядок. Кожен компонент займає фіксований час:

- Складання (інкрементальне): 5-30 с.
- Прошивка додатка: ~5 с.
- Прошивка даних: ~3 с.
- Завантаження: ~2 с до першої спроби WiFi.

Усього ~15 с від редагування до запуску.

### Робота з кількома пристроями на одному хості

ESP-IDF підхоплює змінну середовища `ESPPORT`. Установіть її для
кожного пристрою:

```
$env:ESPPORT="COM4"   # PowerShell
export ESPPORT=/dev/ttyUSB0   # bash
```

Тоді `idf.py flash` і подібні автоматично обирають порт.

## Діагностика аварій

Якщо пристрій застряг у циклі завантаження:

1. **Моніторте його:** аварійний дамп виводиться на послідовний порт.
   Запишіть PC та адреси backtrace.
2. **Декодуйте backtrace:** `idf.py monitor` робить це автоматично.
   Якщо є лише сирий лог, запустіть:
   ```
   addr2line -e build/<project>.elf 0x40012345 0x40012abc
   ```
3. **Типові причини:**
   - Переповнення стеку у новому модулі — збільште
     `CONFIG_MAIN_TASK_STACK_SIZE`.
   - Розіменування невірного вказівника у драйвері — перевірте
     `bindings.json` на невідповідні типи.
   - Спрацювання watchdog — `on_update` модуля блокує. Не блокуйте у
     головній задачі; див.
     **[02-module-author-guide/best-practices.md](../02-module-author-guide/best-practices.md)**.

## Типові помилки

**Неправильний послідовний порт:** ще раз перевірте `COM*` /
`/dev/ttyUSB*` через Device Manager / `dmesg`. `idf.py -p`
перекриває будь-яке значення середовища.

**Відсутній драйвер:** USB-to-serial адаптер (CH340, CP210x) потребує
драйверів ОС. Встановіть із сайту виробника, якщо `idf.py` не може
відкрити порт.

**Прошивка надто повільна / падає:** знизьте швидкість через
`idf.py -b 460800 flash` (типово зазвичай 921600). Дешеві USB-serial
адаптери не витримують повну швидкість.

**Пошкодження LittleFS:** якщо WebUI повертає 404 після скидання до
заводських налаштувань, ви забули `flash_data`. Запустіть його.

**Застарілий кеш складання після зміни таблиці розділів:** очистіть
через `idf.py fullclean`, потім повна перебудова. Зміни таблиці
розділів не завжди підхоплюються інкрементальними збираннями.
