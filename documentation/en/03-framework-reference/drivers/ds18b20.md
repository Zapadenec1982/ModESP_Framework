# `ds18b20` — Dallas OneWire temperature sensor

> 📖 **Українською:** [documentation/uk/03-framework-reference/drivers/ds18b20.md](../../../uk/03-framework-reference/drivers/ds18b20.md)

DS18B20 is а 1-Wire digital temperature sensor (Dallas/Maxim, now ADI).
Each sensor has а unique 64-bit ROM address, so many sensors can sit on
one OneWire bus і be addressed individually. Range -55…+125 °C, resolution
configurable 9-12 bits.

The driver registers as а `sensor` із `capability: temperature` і
`hardware_type: onewire_bus`. `requires_address: false` — the ROM address
need not be set on the binding by hand: sensors are found via bus scan and
assigned to roles (`discovery.assigns: "address"`). `multiple_per_bus: true`
lets multiple sensors share one bound bus. The `requires_address`/`scan`
attributes are per-driver and keyed by WebUI on the bound driver (R3.5).

REQUIRES: ESP-IDF OneWire driver, `modesp_hal`.

## Bindings

```json
{
  "id": "freezer_temp",
  "driver": "ds18b20",
  "hardware_id": "ds18b20_freezer",
  "role": "freezer_temp",
  "bus": "onewire_bus_1",
  "address": "28-3c01a801a2b3"
}
```

`role` declares а capability (`capability: temperature`), not а driver —
Equipment Manager resolves it by role (e.g. `equipment.freezer_temp`), the
source being swappable (R0.1). `bus` references а board-defined OneWire
master. `address` is the ROM (hex із dashes optional); it is optional on the
binding — usually assigned by the scanner.

## Settings (persisted)

| Key | Type | Default | Notes |
|---|---|---|---|
| `read_interval_ms` | int 500-60000 | 1000 | Polling interval. |
| `offset` | float -5…+5 °C | 0.0 | Reading correction (calibration). |
| `resolution` | int 9-12 bits | 12 | Trade-off: 12-bit ≈ 750 ms conversion, 9-bit ≈ 94 ms. |

Settings persist via PersistService under namespace `drv:<binding_id>`.

## Provides

`{"capability": "temperature", "type": "float", "unit": "°C", "range": [-55, 125]}` — published to
`equipment.<role>` by the Equipment Manager.

NaN is published if а conversion fails (CRC mismatch, sensor disconnected).

## Discovery

The driver supports OneWire bus scanning:

```
POST /api/drivers/scan?driver=ds18b20
{"bus": "onewire_bus_1"}
```

Returns an array of `{address, temperature, parasitic}` records. The
inline temperature reading helps you identify which physical sensor is
which (briefly warm one up with your finger).

WebUI exposes а "Scan OneWire bus" button on the driver settings page
що assigns scanned sensors to roles із а few clicks.

## Common pitfalls

**Power glitches → CRC errors:** OneWire is sensitive to long wires
without а 4.7 kΩ pull-up. Use shorter buses or add а terminator. The
driver does one read attempt per tick (no blocking retry loop): on failure
the last valid reading is retained and the attempt is repeated on the next
poll interval; NaN is published only when no valid reading exists yet/anymore.

**Parasitic mode confusion:** Driver auto-detects parasitic power. If
you mix parasitic + powered sensors on one bus, force `parasitic=true`
via board.json (slower conversion but consistent).

**Long conversion at 12-bit:** Don't poll faster than ~1 Hz at 12-bit
resolution. Driver internally serialises conversions on shared buses.

## UI surface

Driver manifest declares а per-binding settings card "DS18B20:
{{hardware_id}}" із number_input (interval), slider (offset), і select
(resolution). Visible on the "Sensor settings" page (service access).

## Why це а good first driver to read

- Demonstrates address-required pattern.
- Demonstrates bus-shared pattern (`multiple_per_bus`).
- Demonstrates discovery з scan endpoint.
- Demonstrates persistence із PersistService.
- ~200 LOC implementation — readable у one sitting.
