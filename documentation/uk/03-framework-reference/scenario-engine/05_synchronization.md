# 05 — Синхронізація між доріжками (семантика порядку тактів)

> 📖 **In English:** [documentation/en/03-framework-reference/scenario-engine/05_synchronization.md](../../../en/03-framework-reference/scenario-engine/05_synchronization.md)

Контракт рушія щодо того, як паралельні доріжки спільно використовують стан.
Вибір зафіксовано в ADR-0003: **порядок тактів, без снапшотів.**

## Основний контракт

1. Рушій тактує екземпляри (дескриптори) у порядку оголошення (handle 1, 2, ...).
2. У межах екземпляра доріжки тактуються у порядку оголошення (доріжка 0, 1, ...).
3. Кожен `SharedState::get()` читає наживо (без снапшоту, без буферизації).
4. `set()` доріжки A видимий для `get()` доріжки B, якщо доріжка B тактується
   ПІЗНІШЕ в тому самому такті (B має більший індекс доріжки).
5. Усі записи доріжок з такту N видимі всім доріжкам під час такту N+1.

## Розгорнутий приклад: виробник → споживач

Рецепт, у якому доріжка 0 ("main") записує сигнал, а доріжка 1 ("watcher")
його читає:

```jsonc
"tracks": [
  { "name": "main",                          // оголошена першою → тактується першою
    "phases": [{
      "name": "signal_phase",
      "entry": [
        {"action": "set_state",
         "params": {"key": "test.flag", "type": "bool", "value": true}}
      ],
      "transitions": [{"to": "$complete"}]
    }]
  },
  { "name": "watcher",                       // оголошена другою → тактується другою
    "phases": [{
      "name": "wait",
      "transitions": [
        {"to": "$complete",
         "when": {"state_key_eq": {"key": "test.flag", "value": true}}}
      ]
    }]
  }
]
```

Трасування:

```
Такт 1 (10 мс):
  Такт доріжки 0 (main):
    - entry-дії фази "signal_phase":
      - invoke_action("set_state") → ctx.state->set("test.flag", true)
                                       ↑
                                       SharedState оновлено негайно;
                                       версія збільшена; зміна відстежена

    - entry-дії завершено; обчислюємо перехід {"to": "$complete"}
      → безумовний вид, спрацьовує негайно
      → залатчуємо target = MODR_TARGET_COMPLETE; running_exit_actions = true

  Такт доріжки 1 (watcher):
    - фаза "wait" — entry-дій немає
    - обчислюємо перехід {"to": "$complete", "when": {state_key_eq...}}
      → виклик evaluate_condition для state_key_eq{test.flag, true}
      → ctx.state->get("test.flag") повертає true (← із запису доріжки 0 У ЦЬОМУ такті)
      → умова виконується → перехід спрацьовує
      → доріжка 1 → COMPLETED

  Перевірка завершення: completion_rule == all_tracks_complete
    → main у ABORTING (виконує exit), watcher у COMPLETED → ще не всі

Такт 2 (20 мс):
  Доріжка 0:
    - exit-дії завершено (у цій фазі їх нема)
    - застосовуємо залатчений перехід → state = COMPLETED

  Доріжка 1:
    - state = COMPLETED → ранній вихід

  Перевірка завершення: all_tracks_complete виконано → сценарій COMPLETED.
```

Watcher перейшов У ТОМУ САМОМУ такті, у якому main писав, — це перевага
порядку тактів. Порядок оголошення «виробник перед споживачем» необхідний
для такої гарантії.

## Розгорнутий приклад: неправильний порядок оголошення (споживач перший)

Той самий рецепт з переставленими доріжками:

```jsonc
"tracks": [
  { "name": "watcher", ... },
  { "name": "main",    ... }
]
```

Трасування:

```
Такт 1 (10 мс):
  Такт доріжки 0 (watcher):
    - обчислюємо перехід state_key_eq(test.flag, true)
      → ctx.state->get("test.flag") повертає nullopt (ще нема)
      → умова false → переходу нема

  Такт доріжки 1 (main):
    - entry: set_state("test.flag", true) — запис відбувається ТЕПЕР
    - залатчує перехід

Такт 2 (20 мс):
  Такт доріжки 0 (watcher):
    - обчислюємо state_key_eq → читає true → спрацьовує
    - watcher → COMPLETED

  Такт доріжки 1 (main):
    - exit-дії (нема) → застосовуємо залатчений COMPLETE
```

Той самий кінцевий стан, але watcher зайняв на 1 такт більше, щоб сходитися.
Це не помилка — лише затримка в 1 такт. Автори рецептів можуть ігнорувати її,
якщо 10 мс затримки прийнятні; для тіснішого зв'язку виправте порядок оголошення.

## Шаблон гонитви (уникати)

Дві доріжки записують той самий ключ на основі спільного стану — у межах одного
такту перемагає останній, хто записав. Уникайте:

```jsonc
"tracks": [
  { "name": "alpha",
    "phases": [{ "entry": [
      {"action": "set_state",
       "params": {"key": "shared.counter", "type": "i32", "value": 1}}
    ], ... }]
  },
  { "name": "beta",
    "phases": [{ "entry": [
      {"action": "set_state",
       "params": {"key": "shared.counter", "type": "i32", "value": 2}}
    ], ... }]
  }
]
```

Результат: `shared.counter` завжди == 2 (beta тактується останньою, перезаписує
alpha). Ймовірно, не те, що задумував автор. Рішення: використовуйте різні
ключі для кожної доріжки.

## Багатотактовий fan-out (детермінований)

Ланцюжок Доріжка 0 → Доріжка 1 → Доріжка 2. Автор оголошує 0, 1, 2:

| Такт | Доріжка 0 | Доріжка 1 | Доріжка 2 |
|------|-----------|-----------|-----------|
| 1 | пише A | читає A → спрацьовує → пише B | читає B → спрацьовує → пише C |
| 2 | (бездіє) | (бездіє) | (бездіє) — усі завершено з такту 1 |

Усі три переходи каскадно відбуваються в одному такті, бо кожна доріжка
тактується ПІСЛЯ свого виробника в тому самому такті рушія.

## Граничний випадок: доріжка читає власний запис

Доріжка 0 викликає `set_state` (пише ключ X), а ПОТІМ обчислює умову, що
читає X у межах тієї самої фази. Трасування:

```
Такт N доріжки 0:
  entry-дії фази:
    - invoke_action set_state → пише X = true
    - повертає ActionStatus::OK
    - ++entry_action_progress
    - return (одна дія за такт)

Такт N+1 доріжки 0:
  entry-дії фази:
    - усі entry-дії виконано (з такту N)
    - обчислюємо переходи
    - state_key_eq{X, true} → читає X = true → спрацьовує
```

Доріжка бачить власний запис на НАСТУПНОМУ такті, не в тому самому. Це
наслідок політики «одна дія за такт»: переходи фази обчислюються ПІСЛЯ
завершення всіх entry-дій, що займає ≥ entry_action_n тактів.

Для миттєвої самосинхронізації використовуйте:
- Складену умову вже в логіці відгуку entry-дії
- Або просто структуруйте фазу так, щоб entry встановлював стан, а переходи
  перевіряли іншу умову (не той ключ, який щойно встановлено)

## Антипатерни

### 1. Циклічне очікування

Доріжка A чекає на сигнал доріжки B; доріжка B чекає на сигнал доріжки A.
Обидві доріжки зависають назавжди. Рушій цього не виявляє; `phase_timeout_ms`
служить запобіжником (зрештою одна або обидві фази вичерпають час → FAILED).

Рішення: переробити рецепт так, щоб щонайменше одна доріжка мала перехід
за часом або самодостатній перехід.

### 2. Миттєва видимість «запис-потім-читання» у тому самому такті

```jsonc
"entry": [
  {"action": "set_state", "params": {"key": "x", "type": "bool", "value": true}}
],
"transitions": [
  {"to": "next", "when": {"state_key_eq": {"key": "x", "value": true}}}
]
```

Автор очікує, що перехід спрацює одразу в тому ж такті. Так НЕ відбувається —
entry-дія виконується на такті N, перехід обчислюється на такті N+1 (або
пізніше, якщо entry-дій декілька). Якщо мається на увазі миттєве просування,
використовуйте безумовний перехід (`{"to": "next"}`).

### 3. Гонитва дескрипторів при читанні між екземплярами

Екземпляр 1 і екземпляр 2 ТОГО САМОГО рецепта обидва пишуть у
`<recipe>.foo` (той самий дзеркальний ключ, бо обидва мають однакове ім'я
рецепта). Перемагає останній — такт екземпляра 2 відбувається після такту
екземпляра 1, тож записи екземпляра 1 одразу затираються.

Рішення: не завантажуйте декілька екземплярів рецептів, які мають спільні
ключі виводу. Або робіть ключі виводу прив'язаними до екземпляра (Етап 1.5 —
наразі API для цього нема).
