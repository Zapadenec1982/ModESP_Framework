# `ld2410b` — 24 GHz mmWave presence radar

> 📖 **Українською:** [documentation/uk/03-framework-reference/drivers/ld2410b.md](../../../uk/03-framework-reference/drivers/ld2410b.md)

HLK-LD2410B is a 24 GHz mmWave human-presence radar. It detects both **moving** and **stationary** targets up to ~6 m and streams frames over UART (256000 8N1) carrying: presence state, moving/stationary target distance (cm), and per-gate energy. Unlike a PIR, it sees a motionless person (sitting/sleeping).

The driver registers as a `sensor` with `hardware_type: uart_bus`, `requires_address: false`, `multiple_per_bus: true`. **The HAL owns the UART port** (board.json `uart_buses` section) — the driver only reads bytes and parses the `F4 F3 F2 F1 … F8 F7 F6 F5` frame protocol.

REQUIRES: ESP-IDF `driver` (UART), `modesp_hal`.

## Hardware (board.json)

```json
"uart_buses": [
  { "id": "uart_1", "port": 1, "rx": 18, "tx": 17, "baud": 256000 }
]
```

| Field | Meaning |
|---|---|
| `port` | UART peripheral (1/2; **0 is the console**). |
| `rx` | MCU RX ← sensor TX (**required** — frames arrive here). |
| `tx` | MCU TX → sensor RX (optional — only for config commands, see below). |
| `baud` | 256000 (LD2410 factory default). |

UART logic is **3.3 V** even when powered at 5 V, so it wires directly to the ESP32 — no level shifter.

## Bindings & address channels

One physical sensor exposes several values. Since `read()` returns a single number, **the `address` field selects the channel** (like the ROM in DS18B20). Several roles may share one UART bus (`multiple_per_bus`), each with a **distinct** `address`:

| `address` | Channel | Units |
|---|---|---|
| `presence` (or empty) | any target present | 0/1 |
| `moving` | moving target distance | cm |
| `static` | stationary target distance | cm |
| `detect` | detection distance | cm |
| `moving_energy` | moving target energy | 0-100 |
| `static_energy` | stationary target energy | 0-100 |

```json
{"hardware": "uart_1", "driver": "ld2410b", "role": "presence",       "address": "presence", "module": "equipment"},
{"hardware": "uart_1", "driver": "ld2410b", "role": "move_distance",  "address": "moving",   "module": "equipment"},
{"hardware": "uart_1", "driver": "ld2410b", "role": "still_distance", "address": "static",   "module": "equipment"}
```

EquipmentBase publishes each role to `equipment.<role>` (e.g. `equipment.presence`, `equipment.move_distance`). The first binding on a port becomes the **owner** (reads the UART + configures the radar); the rest are passive views onto the same decoded frame.

## Read architecture

```
LD2410B ──UART──▶ Ld2410Port (shared per-port frame parser)
                      │
        ┌─────────────┼─────────────┐
   presence       move_distance   still_distance   ← Ld2410bDriver (per channel)
        │             │             │
        └──── equipment.<role> ◀── EquipmentBase (calls read(), publishes)
                      │
              presence module ── presence.detected / presence.state / …
```

## Sensor configuration (bindings `settings`, build-time)

At init the owner instance **writes config into the radar** via the LD2410 command protocol (`FD FC FB FA … 04 03 02 01`). This **requires `tx` wired** (MCU TX → sensor RX); without it the commands are ignored and the radar keeps its factory settings (reading still works).

| Key | Type | Default | Meaning |
|---|---|---|---|
| `absence_s` | int 0-600 s | 1 | Radar "no-one duration" — **reaction speed** (factory ~5 s → slow). |
| `max_cm` | int 75-600 cm | 600 | Native distance gate (quantised to 0.75 m). The radar stops detecting past it. |
| `move_sens` | int 0-100 | 0 | Moving sensitivity threshold (0 = leave default; higher = less sensitive). |
| `still_sens` | int 0-100 | 0 | Static threshold (0 = leave default; **raise to fight phantom presence** from stationary objects). |
| `timeout_ms` | int 200-10000 | 2000 | No frame for longer → `is_healthy() = false` (driver-side only). |

> ⚠️ This is **static config** (applied once at init from bindings.json). Driver settings do NOT reach the web UI — by framework design, web-tunable settings are **module state keys only** (see below).

## Web-tunable settings (via the presence module, runtime)

Live-tunable parameters are declared as **module state keys** in [`modules/presence`](../../../../modules/presence/manifest.json) (`access: readwrite`, `persist: true`) — the generator wires them into the web UI, NVS, and MQTT automatically:

| Key | Meaning | Requires |
|---|---|---|
| `presence.max_distance` | Software distance filter (cm-precise, 10 cm step) — ignore targets beyond | bound `move_distance`/`still_distance` channels |
| `presence.hold_sec` | Occupancy hold after the target clears | — |
| `presence.enabled` | Enable/disable detection | — |

This is the canonical manifest-driven pattern: distance/hold are tuned live from the web (the module gates in software), while deep sensor config (reaction/sensitivity) is build-time in bindings.

## Provides

`{"type": "float"}` — the channel value is published to `equipment.<role>`. For the presence channel: 0/1; for distances: cm; for energies: 0-100.

## Optionality (Kconfig)

The driver is **optional automatically** — the generator emits a toggle under the **"ModESP Drivers"** menu:

```
CONFIG_MODESP_DRIVER_LD2410B   (default y)
```

- `idf.py menuconfig` → ModESP Drivers → uncheck "ld2410b driver" → the driver code is **not compiled** (smaller binary) and `modesp_register_all_drivers()` skips it (guarded by `#ifdef`).
- Board consistency: if a board binds `ld2410b` while the toggle is off, the **build fails with FATAL**. Reconcile with `python tools/drivers_sync.py --fix` (enable required) / `--prune` (disable drivers the active board doesn't use).
- No manual Kconfig edits: `components/modesp_hal/Kconfig` is generated (do not edit).

The presence **module** (`modules/presence`) is listed in `project.json`, so it always compiles (framework convention: drivers are Kconfig-optional, business modules are not). It is lightweight and **inert without a bound driver** (`equipment.presence` is never published → `presence.state = none`).

## Common issues

**Slow reaction (presence lingers ~5-12 s after leaving):** the radar's factory "no-one duration" (~5 s) plus the module `hold_sec`. Set `absence_s` low (needs TX!) and `presence.hold_sec` = 0-1 in the web UI.

**"Always present" / phantoms:** the radar detects stationary targets (furniture/reflections) with a high default sensitivity. Raise `still_sens` (e.g. 60) in bindings (needs TX).

**Distance filter "doesn't work":** either (1) `presence.max_distance` = 0 (disabled), or (2) no distance channel bound (`move_distance`/`still_distance`) so the module has nothing to compare. No-TX option is the software gate; with TX, the native `max_cm`.

**HAL shows `0 uart` / binding skipped:** stale `data` partition. board.json is copied into `data/` at configure time → rebuild so CMake reconfigures (a board.json change is already in `CMAKE_CONFIGURE_DEPENDS`).
