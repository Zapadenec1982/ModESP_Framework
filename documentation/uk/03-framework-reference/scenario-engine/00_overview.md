# 00 — Огляд рушія сценаріїв

> 📖 **In English:** [documentation/en/03-framework-reference/scenario-engine/00_overview.md](../../../en/03-framework-reference/scenario-engine/00_overview.md)

## Що це

`components/modesp_scenario/` — це **повторно використовувана бібліотека для побудови довільних часозалежних алгоритмів**, яку C++ бізнес-модулі ModESP_v4 програмно викликають для виконання фазових сценаріїв із часовим планом.

Рушій вирішує одну конкретну проблему: **сьогодні бізнес-модулі дублюють логіку часових планів вручну** (скінченні автомати, лічильники фаз, охоронці переходів) і змушені складно синхронізувати кілька паралельних процесів. Рушій надає композовні примітиви.

## Аудиторія

**Основний користувач:** C++ автори бізнес-модулів (мультиварка, ферментер, лабораторний термоцикл, контролер поливу тощо). Рушій — це їхня бібліотека.

**НЕ є користувачем:** кінцеві користувачі у WebUI. Створення сценаріїв через UI — це окрема надбудова, **поза межами цього рушія**.

## Які проблеми розв'язує

1. **Фазові часові плани з переходами** — без ручних `state enum` + лічильників.
2. **Паралельні доріжки в межах ОДНОГО сценарію** (як доріжки MIDI) — без власної синхронізації між підпрограмами бізнес-модуля.
3. **Кілька незалежних екземплярів сценаріїв** (до `MAX_SEQUENCES` одночасно, типово 2 — Kconfig `CONFIG_MODESP_MAX_SEQUENCES`) — управління дескрипторами бере на себе рушій.
4. **Арбітраж ресурсів** (ISA-88 §5.3) — рецепт декларує потрібні ресурси, рушій гарантує відсутність конфліктів на старті.
5. **Відновлення після зникнення живлення** — стан токенів, збережений у NVS, відновлює позицію фази при завантаженні.
6. **Доменно-незалежні примітиви** + розширюваність через `ActionRegistry` — доменні модулі додають власні дії без змін у самому рушії.

## Чого рушій НЕ робить

- Створення сценаріїв у WebUI (поза межами рушія).
- Жорсткий реальний час (рушій працює з частотою 100 Гц; для щільніших циклів потрібна пряма логіка модуля).
- Міжмодульний арбітраж апаратури (етап 1.5; у MVP — «останній запис перемагає»).
- Перевірка моделі під час компіляції / формальна верифікація (компілятор ловить деякі семантичні помилки, але не виявляє взаємних блокувань).

## Цільова апаратура

- **Базова:** ESP32-WROOM-32 (мінімальна специфікація, основна ціль розробки).
- Код рушія не залежить від цілі завдяки абстракції ESP-IDF; інші варіанти ESP32 працюють «з коробки».
